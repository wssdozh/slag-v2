# RELEASING.md — версии, каналы и выпуск SLAG

> Регламент для агента и разработчика. Связанные файлы: `src-tauri/src/updater.rs`,
> `scripts/release-meta.mjs`, `scripts/release.mjs`, `.github/workflows/release.yml`, `BUILD.md`.

## 1. Как это устроено

Клиент не использует `tauri-plugin-updater`: он десктопный и ставит nsis-установщик, а у нас
портативная exe и apk. Вместо этого:

- манифест `latest.json` лежит ассетом в релизе; у каждого канала свой адрес (см. §3.2);
- клиент сверяет `version` (semver) со своей, качает файл своей платформы, проверяет **sha256**
  и **minisign-подпись** вшитым публичным ключом (`src-tauri/updater.pubkey`);
- только после обеих проверок файл применяется:
  - **windows, портативная папка**: скачанный exe запускается как `--apply-update <target> <pid>`,
    меняет файл местами, ждёт выхода старого процесса и поднимает новый;
  - **windows, установка в папку без прав записи** (обычно `Program Files`): клиент качает
    nsis-установщик и запускает его;
  - **android**: apk кладётся в `cacheDir/updates`, kotlin-плагин отдаёт его системному
    установщику через `FileProvider`; система спрашивает «Обновить?»;
  - **linux, AppImage**: приложение владеет ровно одним файлом — тем, что запущено
    (`$APPIMAGE`). новый образ качается, проверяется и заменяет старый через `rename()` рядом с
    ним (атомарно, без root), после чего запускается заново; старый процесс дохнет, его FUSE-моунт
    никому не мешает. это единственная linux-форма, которая обновляется сама;
  - **linux, пакет** (deb, rpm, Arch `.pkg.tar.zst`) и **flatpak**: файлы принадлежат
    apt/dnf/pacman/flatpak, приложение их не трогает. вкладка «Обновления» показывает новую
    версию, команду обновления и ссылку на страницу релиза — никаких sudo из GUI.

Обе подписи (`*.sig` рядом с артефактом и поле `signature` в манифесте) — это **base64** от
armored minisign-текста, как их пишет `tauri signer`. `updater.rs` разворачивает base64 перед
`minisign_verify::Signature::decode`; голый armored-блок клиент тоже примет (там есть фолбэк).

Подпись самого манифеста не проверяется: url ограничен префиксом
`https://github.com/wssdozh/slag-v2/releases/download/`, а подменённый файл не пройдёт проверку
подписи. Заметки о релизе — справочные.

## 1a. Как читать логи обновления

Каждый шаг нативного пайплайна (адрес манифеста и канал, его версия, старт и конец скачивания,
размер, sha256, подпись, выбранный способ применения, запуск установщика/хелпера) уходит в событие
`slag://update-log`. Фронт перекладывает его в общий лог со scope `UPDATE`, поэтому всё видно в
«Настройки → Логи & Диагностика», без консоли и без adb. Строка «манифест» на вкладке
«Обновления» показывает фактический адрес — если он не тот, что ожидался, значит задан
`SLAG_UPDATE_ENDPOINT`.

Ошибки приходят кодами (`network`, `http_404`, `verify_failed`, `signature_invalid`,
`unknown_channel`, `permission_required`, `restart_failed`, …). В UI они не висят строкой в
карточке: ошибка показывается тостом с русским текстом (`updateErrorText`), а «разрешить
установку из этого источника» — вопросом через `confirmAction`. Для диагностики смотри последние
строки `[update] …` в stderr (`adb logcat -s RustStdoutStderr`).

## 1b. linux: кто владеет файлом

Обновление на linux — не техническая, а юридическая задача: файл принадлежит либо приложению,
либо пакетному менеджеру. Отсюда три разных поведения, и приложение выбирает их само, а не по
желанию пользователя.

| как поставлено | кто обновляет | что показывает вкладка «Обновления» |
|---|---|---|
| AppImage | приложение | «обновить»: скачать, проверить sha256 и подпись, подменить `$APPIMAGE`, перезапуститься |
| deb / rpm | apt / dnf | новую версию, кнопку на страницу релиза и подпись «поставлен пакетом — обнови через apt / dnf» |
| Arch `.pkg.tar.zst` | pacman | то же |
| flatpak | flatpak | то же, но с командой `flatpak update com.slag.notes` |

Как определяется форма: `updater.rs` смотрит на `$APPIMAGE` (его выставляет рантайм AppImage),
потом на `/.flatpak-info`, иначе считает установку пакетной. Никакой эвристики по путям — deb
можно распаковать в любую папку и запустить оттуда.

Почему не обновлять пакет изнутри приложения:

- файл в `/usr` принадлежит dpkg/rpm/pacman; подменив его, приложение оставит базу пакетов
  врать, а следующее `apt upgrade` вернёт старую версию или сломает установку;
- для этого нужен root, то есть sudo-диалог из GUI — ровно то, чего просят не делать;
- upstream tauri-plugin-updater тоже считает AppImage единственным «своим» артефактом; deb и rpm
  он умеет ставить, но через тот же sudo-диалог.

Альтернатива, которая «правильно» для deb/rpm, — свой APT-репозиторий (reprepro или Cloudsmith)
и обычный `apt upgrade`. Это отдельная инфраструктура: подпись репозитория, метаданные на каждый
релиз, хостинг. Пока не заведено, поэтому честнее показать команду, чем притворяться, что
приложение обновилось.

Дельта-обновления (zsync, `appimageupdatetool`) сознательно не делаем: образ ~20 МБ, полная
загрузка проще и не требует вшивать в AppImage update-information.


## 2. Ключи

Один раз на машине сборки:

```powershell
npx tauri signer generate -w "$env:USERPROFILE\.tauri\slag-updater.key" --ci
```

- `~/.tauri/slag-updater.key` — приватный, **только локально**, без пароля (в `~/.tauri`, вне репо).
- `~/.tauri/slag-updater.key.pub` — содержимое (base64) уже скопировано в
  `src-tauri/updater.pubkey` и закоммичено. Менять только при ротации ключа: клиент, собранный
  со старым ключом, после ротации перестанет принимать обновления и его придётся обновить вручную.

Потеря ключа = невозможность обновить уже установленные копии, кроме ручной переустановки.
В CI ключ приходит секретом `TAURI_SIGNING_PRIVATE_KEY`, в файловой системе раннера его нет.

## 3. Версии и каналы

### 3.1. Что означают цифры

Версия — обычный semver `major.minor.patch`, источник правды — `src-tauri/tauri.conf.json`
(в `package.json` и `Cargo.toml` она должна совпадать).

| цифра | когда растёт | пример |
|---|---|---|
| `patch` | фиксы, косметика, тексты; данных и протокола не касается | 0.2.5 → 0.2.6 |
| `minor` | новая функциональность, обратно совместимая; **до 1.0 сюда же идут ломающие изменения** | 0.2.6 → 0.3.0 |
| `major` | ломающее изменение, требующее миграции данных или несовместимого протокола | 0.9.0 → 1.0.0 |

Почему до 1.0 ломающее идёт в `minor`: при `major = 0` никто не ждёт стабильного API, а
`0.x.0` читается как «здесь могло сломаться». Как только выходит 1.0.0, `major` становится
обещанием: **формат заметок на диске, формат бандла синка (`schemaVersion`) и протокол релея не
меняются внутри одной мажорной версии**. Всё, что их меняет, — это 2.0.0 плюс миграция.

Ломающим считается:

- поле во frontmatter, которое старый клиент не поймёт (а не просто не покажет);
- `schemaVersion` бандла синка — растёт только вместе с мажором приложения;
- формат `.attachments/` или `.trash/`, после которого старые файлы не читаются;
- формат `latest.json`, который перестанет понимать уже установленный клиент.

Новое поле, которое старый клиент молча игнорирует, ломающим не считается: это `minor`.

Предрелизные версии — тот же semver с суффиксом: `1.2.4-dev.42`, `1.2.4-beta.3`.
`1.2.4-dev.42 < 1.2.4-beta.3 < 1.2.4`: бета новее дев-сборки, релиз новее обеих.

### 3.2. Каналы

Канал — то, откуда клиент читает обновления. Их три, переключатель — «Настройки → Обновления →
канал», значение лежит в `localStorage['slag_update_channel']` (на устройстве, синком не ездит),
по умолчанию `release`.

| канал | что в нём | адрес манифеста |
|---|---|---|
| `release` | только стабильные релизы | `…/releases/latest/download/latest.json` (github `latest`) |
| `beta` | предрелизы, готовые к проверке | `…/releases/download/beta/latest.json` |
| `dev` | каждая сборка `master` | `…/releases/download/dev/latest.json` |

`beta` и `dev` — **rolling-теги**: релиз с таким тегом один, его ассеты и `latest.json`
перезаписываются каждой сборкой, а сами сборки лежат в отдельных релизах `v<версия>`, чтобы
старую бету можно было скачать руками. Стабильный релиз всегда получает свой тег и становится
github-овским `latest`; предрелизы туда не попадают, поэтому клиент на `release` их не увидит
никогда — даже если про них знает.

Ключевое правило: **`src-tauri/tauri.conf.json` всегда держит следующую нерелизнутую версию.**
Релиз тегирует её как есть, предрелизная сборка добавляет суффикс. Поэтому `0.2.6-dev.7` новее
выпущенного `0.2.5` и по semver, и по `versionCode`.

### 3.3. versionCode для android

Системный установщик android сравнивает `versionCode`, а не `versionName`. Tauri считает его из
версии по формуле:

```
versionCode = major * 1_000_000 + minor * 1_000 + patch
```

Следствия, которые надо помнить:

- `1.2.4-dev.42` и `1.2.4` дают **один и тот же** `versionCode` — апгрейд с беты на релиз
  система может отклонить как «не новее». Поэтому бета режется от следующего патча, а не от
  текущего: пока в репозитории `0.2.6`, бета — `0.2.6-beta.N`, а не `0.2.5-beta.N`;
- `minor` и `patch` обязаны оставаться меньше 1000. Потолок не мешает: `major` можно гнать до
  2100 при лимите android в 2 100 000 000;
- менять формулу нельзя: у уже установленных клиентов `versionCode` посчитан по ней, и сдвиг
  сделает следующее обновление «старее» текущего.

### 3.4. Откат

Версии сравниваются semver-ом, откат запрещён. Откатиться можно только выпуском версии выше —
например, `0.2.7` с содержимым `0.2.6`. Манифест старого релиза не переписывается. Канал при
этом меняется свободно: переключение на `release` с беты просто перестаёт предлагать беты,
установленная версия остаётся.

## 4. Выпуск

Всё делает `.github/workflows/release.yml`. Ручных шага два: поднять версию в репозитории и
поставить тег (либо запушить в `master`, если нужна дев-сборка).

| действие | что получается |
|---|---|
| push в `master` | `dev`: версия `<версия из tauri.conf.json>-dev.<run>`, prerelease на теге `dev`, собираются windows + android |
| тег `v1.2.3` | `release`: обычный релиз, становится `latest`, собираются windows, linux, android, arch |
| тег `v1.2.3-beta.4` | `beta`: prerelease, свой релиз плюс перезаписанный `latest.json` на теге `beta` |
| Actions → release → Run workflow | то же, что push в `master`, но канал можно выбрать (`dev` / `beta`) |

Стабильный релиз **нельзя** выпустить кнопкой: только тегом. Это защита от «нажал и уехало
всем». Тег и версия в `tauri.conf.json` обязаны совпадать, иначе `prepare` падает до сборки.

Порядок стабильного релиза:

1. `src-tauri/tauri.conf.json`, `package.json`, `Cargo.toml` — одна и та же версия, например
   `0.3.0`. Коммит «chore: release 0.3.0».
2. `git tag v0.3.0 && git push origin v0.3.0`.
3. Дождаться зелёного `release`. Заметки берутся из коммитов между прошлым тегом и этим, если в
   `Run workflow` ничего не вписали.
4. Сразу после релиза поднять версию до следующей (`0.3.1`) отдельным коммитом — с этого момента
   дев-сборки снова «новее» релиза.

### локально

Тот же код, что в CI:

```bash
node scripts/release-meta.mjs --ref refs/tags/v1.2.3 --base 1.2.3 --notes "что поменялось"
node scripts/release.mjs --version 1.2.3 --channel release --notes-file notes.md \
  --repo wssdozh/slag-v2 slag-v2.exe SLAG-1.2.3-setup.exe SLAG-1.2.3.apk
```

`--dry-run` собирает манифест и staging-папку, но не зовёт `gh`. Подпись — ключ из
`~/.tauri/slag-updater.key` (`--key`) или из `TAURI_SIGNING_PRIVATE_KEY`.

### проверки на каждый пуш

`ci.yml` на ubuntu гоняет `pnpm install --frozen-lockfile`, `npm run check`,
`node --test scripts/release-meta.test.mjs`, `npm run build` и `e2e/slag` на одном воркере.
`--frozen-lockfile` заодно доказывает, что патч `@atomic-editor` из `patches/` применяется на
чистой установке.

### секреты

`TAURI_SIGNING_PRIVATE_KEY` (содержимое ключа), `ANDROID_KEYSTORE_BASE64`,
`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. Без keystore android
джоб падает мягко: релиз уходит без apk, и в манифесте просто нет android-записи.

## 5. Проверка обновления вживую

Механику удобно гонять локально, не публикуя релиз:

```powershell
# фикстура: папка с latest.json и файлами, раздаётся любым http-сервером
$env:SLAG_UPDATE_ENDPOINT = 'http://127.0.0.1:8765/latest.json'
.\src-tauri\target\release\slag-v2.exe
```

`SLAG_UPDATE_ENDPOINT` подменяет только адрес манифеста; подпись, sha256 и префикс url при этом
не ослабляются (для локального адреса разрешены любые `http(s)://` url, но файл всё равно должен
пройти подпись). Переменная живёт в `updater.rs` (`endpoint()`), в релизной сборке просто не
задаётся.

Без GUI, из терминала:

```powershell
$env:SLAG_UPDATE_CHANNEL = 'beta'   # без переменной — release
.\src-tauri\target\release\slag-v2.exe --update-check
```

Чек-лист:

- [ ] вкладка «Обновления»: версия, платформа, канал, «проверить»;
- [ ] переключение канала меняет адрес в строке «манифест» и переспрашивает версию;
- [ ] «нет связи» (без сети) — ошибка текстом, приложение не падает;
- [ ] битый sha256 / подпись — «обновление отменено», файл не запускается;
- [ ] windows: кнопка «скачать и установить» → прогресс → приложение перезапускается,
      `slag-v2.exe` на диске новой версии, `.old-*` не копится;
- [ ] windows + установка в `Program Files`: кнопка «скачать установщик» → установщик поверх;
- [ ] android: «обновить» → системный установщик → «Обновить» → данные на месте;
- [ ] linux (AppImage): «обновить» → файл заменён, приложение поднялось уже новым;
- [ ] linux (deb/rpm/arch/flatpak): версия показывается, кнопка ведёт на страницу релиза,
      подпись под ней называет команду пакетного менеджера.

## 6. Что осталось за рамками

- подпись windows-установщика (code signing certificate): smartscreen может ругаться на
  установщик, скачанный впервые; портативная подмена этого не касается;
- подпись манифеста (см. §1);
- истории бет в манифесте нет: `latest.json` канала перезаписывается целиком, старые сборки
  лежат только в релизах `v<версия>`.
