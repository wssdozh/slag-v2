# RELEASING.md — как выпускать и проверять обновления SLAG

> Регламент для агента и разработчика. Связанные файлы: `src-tauri/src/updater.rs`,
> `scripts/publish-release.ps1`, `BUILD.md`.

## 1. Как это устроено

Клиент не использует `tauri-plugin-updater`: он десктопный и ставит nsis-установщик, а у нас
портативная exe и apk. Вместо этого:

- манифест `latest.json` лежит ассетом в публичном релизе
  `https://github.com/wssdozh/slag-v2/releases/latest/download/latest.json`;
- клиент сверяет `version` (semver) со своей, качает файл своей платформы, проверяет **sha256**
  и **minisign-подпись** вшитым публичным ключом (`src-tauri/updater.pubkey`);
- только после обеих проверок файл применяется:
  - **windows, портативная папка**: скачанный exe запускается как `--apply-update <target> <pid>`,
    меняет файл местами, ждёт выхода старого процесса и поднимает новый. сам exe — единственный
    артефакт, приложение остаётся портативным;
  - **windows, установка в папку без прав записи** (обычно `Program Files`): клиент качает
    nsis-установщик и запускает его; установщик ставит поверх;
  - **android**: apk кладётся в `cacheDir/updates`, kotlin-плагин отдаёт его системному
    установщику через `FileProvider`; система спрашивает «Обновить?»;
  - **linux**: приложение не трогает свой бинарь (им владеет пакетный менеджер): вкладка
    «Обновления» показывает новую версию и ссылку на страницу релиза.

Подпись манифеста не проверяется: url ограничен префиксом
`https://github.com/wssdozh/slag-v2/releases/download/`, а подменённый файл не пройдёт
проверку подписи. Заметки о релизе — справочные.

Обе подписи (`*.sig` рядом с артефактом и поле `signature` в манифесте) — это **base64** от
armored minisign-текста, как их пишет `tauri signer`. `updater.rs` разворачивает base64 перед
`minisign_verify::Signature::decode`; если класть в `signature` голый armored-блок, клиент тоже
его примет (там есть фолбэк).

## 1a. Как читать логи обновления

Каждый шаг нативного пайплайна (адрес манифеста, его версия, старт и конец скачивания, размер,
sha256, подпись, выбранный способ применения, запуск установщика/хелпера) уходит в событие
`slag://update-log`. Фронт перекладывает его в общий лог со scope `UPDATE`, поэтому всё видно в
«Настройки → Логи & Диагностика» (и в файле логов), без консоли и без adb. Там же строка
«канал» на вкладке «Обновления» показывает фактический адрес манифеста — если он не тот, что
ожидался, значит задан `SLAG_UPDATE_ENDPOINT`.

Ошибки приходят кодами (`network`, `http_404`, `verify_failed`, `signature_invalid`,
`permission_required`, `restart_failed`, …). В UI они не висят строкой в карточке: ошибка
показывается тостом с русским текстом (`updateErrorText`), а «разрешить установку из этого
источника» — вопросом через `confirmAction`, потому что это решение, а не сообщение. В логе
UPDATE остаются исходные коды и данные. Для диагностики смотри последние строки `[update] …` в
stderr (`adb logcat -s RustStdoutStderr`).

## 2. Ключи

Один раз на машине сборки:

```powershell
npx tauri signer generate -w "$env:USERPROFILE\.tauri\slag-updater.key" --ci
```

- `~/.tauri/slag-updater.key` — приватный, **только локально**, без пароля (в `~/.tauri`, вне репо).
- `~/.tauri/slag-updater.key.pub` — содержимое (base64) уже скопировано в
  `src-tauri/updater.pubkey` и закоммичено. Менять только при ротации ключа: клиент, собранный
  со старым ключом, после ротации перестанет принимать обновления и его придётся обновить вручную.

Потеря ключа = невозможность обновить уже установленные копии, кроме ручной переустановки.

## 3. Репозиторий релизов

Проект открытый, поэтому релизы живут в нём же: `github.com/wssdozh/slag-v2/releases`. Отдельный
репозиторий артефактов (`slag-releases`) больше не нужен и удаляется; прежние теги там остаются
только историей и клиентами не читаются.

## 4. Выпуск

### через ci (основной путь)

`.github/workflows/release.yml`, кнопка **Run workflow**. Спрашивает три обязательных поля:

- `version` — x.y.z, **уже стоящая в `src-tauri/tauri.conf.json`** (джоб `verify` падает, если не
  совпало: манифест не должен обещать версию, которой нет в бинарниках);
- `channel` — `stable` / `beta` / `alpha` / `dev`;
- `notes` — что поменялось (уходит в заметки релиза и `latest.json`).

Собирает windows (exe + nsis), linux (deb + AppImage) и android (apk, подпись из секретов) из
одного коммита, затем публикует тем же `publish-release.ps1`. Секреты:
`TAURI_SIGNING_PRIVATE_KEY`, `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`,
`ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD`. Пароль к ключу обновлений не используется:
ключ создан без пароля, отдельного секрета для него нет.

**Каналы — это фильтр.** `stable` создаёт обычный релиз и становится github-овским `latest` —
единственный адрес, который читает установленный клиент. `beta`/`alpha`/`dev` уходят как
**prerelease**, `latest` не трогают, и обычный клиент их не видит: поставить их можно только
скачав файл со страницы релиза. Отдельного переключателя каналов в клиенте нет намеренно.

### локально

1. Собери release apk (windows-хост, см. `BUILD.md` §7) и подпиши его `debug.keystore`:
   `zipalign -p -f 4`, `apksigner sign --ks ... --ks-key-alias androiddebugkey`. Версия
   (`versionName`/`versionCode`) берётся из `src-tauri/tauri.conf.json`: бампает её скрипт,
   `versionCode = major*1e6 + minor*1e3 + patch`.
2. Запусти публикацию (сам бампнет версию в `tauri.conf.json`, `Cargo.toml`, `package.json`,
   прогонит `check`/`build`, соберёт desktop-бандл, подпишет всё и зальёт):

```powershell
pwsh scripts/publish-release.ps1 -Version 0.2.0 -Notes "что поменялось" -ApkPath .tmp\SLAG-0.2.0-universal.apk
```

Если apk ещё не собран — `-SkipAndroid` (тогда android-запись в манифест не попадёт и клиент на
телефоне увидит «в релизе нет файла для этой платформы»).

Флаги: `-SkipBuild` (взять уже собранное), `-Repo`, `-KeyPath`.

3. Скрипт сам проверяет, что `releases/latest/download/latest.json` отдаёт новую версию. Если
   github ещё кэширует — повторить `Invoke-WebRequest` через минуту.

### arch

Пакет `.pkg.tar.zst` собирается из того же `.deb`, без повторной сборки Rust: джоб `arch` в
`release.yml` поднимает `archlinux:latest` в docker, ставит `base-devel`, и
`scripts/pack-arch.sh` перепаковывает deb через `makepkg` (зависимости — `webkit2gtk-4.1`,
`libappindicator-gtk3`, `librsvg`, `gtk3`, `libsoup`). Результат идёт в `ExtraAssets` и просто
прикрепляется к релизу: клиент на linux себя не обновляет.

### проверки на каждый пуш

`ci.yml` на ubuntu гоняет `pnpm install --frozen-lockfile`, `npm run check`, `npm run build` и
`e2e/slag` на одном воркере. `--frozen-lockfile` заодно доказывает, что патч `@atomic-editor`
из `patches/` применяется на чистой установке. релиз по-прежнему только руками.

## 5. Проверка обновления вживую

Механику удобно гонять локально, не публикуя релиз:

```powershell
# фикстура: папка с latest.json и файлами, раздаётся любым http-сервером
$env:SLAG_UPDATE_ENDPOINT = 'http://127.0.0.1:8765/latest.json'
.\src-tauri\target\release\slag-v2.exe
```

`SLAG_UPDATE_ENDPOINT` подменяет только адрес манифеста; подпись, sha256 и префикс url при этом
не ослабляются (для локального адреса разрешены любые `http(s)://` url, но файл всё равно должен
пройти подпись). Переменная живёт в `updater.rs` (`endpoint()`), в релизной сборке просто не
задаётся.

Чек-лист:

- [ ] вкладка «Обновления»: версия, платформа, «проверить»;
- [ ] «нет связи» (без сети) — ошибка текстом, приложение не падает;
- [ ] битый sha256 / подпись — «обновление отменено», файл не запускается;
- [ ] windows: кнопка «скачать и установить» → прогресс → приложение перезапускается,
      `slag-v2.exe` на диске новой версии, `.old-*` не копится;
- [ ] windows + установка в `Program Files`: кнопка «скачать установщик» → установщик поверх;
- [ ] android: «скачать apk» → системный установщик → «Обновить» → данные на месте;
- [ ] linux: версия показывается, кнопка ведёт на страницу релиза.

## 6. Откат

Версии сравниваются semver-ом и откат запрещён. Откатиться можно только выпуском версии выше
(например, 0.2.1 с содержимым 0.2.0) — это и есть штатный откат. Манифест старого релиза не
переписать.

## 7. Что осталось за рамками

- подпись windows-установщика (code signing certificate): smartscreen может ругаться на
  установщик, скачанный впервые; портативная подмена этого не касается;
- подпись манифеста (см. §1);
- ci: всё собирается локальным скриптом; при желании `tauri-action` + `latest.json` из
  `includeUpdaterJson` заменят шаг 2, но android-apk всё равно требует отдельного шага.
