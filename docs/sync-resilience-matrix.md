# Необычные сценарии отказов синхронизации SLAG

Аудит исходников `54941581`. Три независимых обзора: смысл данных, релей, диск/UX. A/B/C — три синтетические реплики; `r` — общая подтверждённая база. `Воспроизведено` ниже означает запуск функции слияния или `NoteReplica` с синтетической лентой, **не** прогон установленных клиентов. Остальные строки — кандидаты для регрессий. Рабочая комната, профили и пользовательские файлы не использовались.

## 1. Подтверждено локальными пробами

**Исправлено в ветке отказоустойчивости, ещё не в `dev.81`.** Для S1 и S2 неоднозначное слияние не отправляется: три реплики применяют эталон, полные локальные варианты сохраняются на разбор. Эквивалентный чеклист и привязка вложения по ID не создают лишний конфликт. Для S3 совпавшее некаскадное обновление больше не открывает разбор, для S4 одиночные напоминания сравниваются как моменты только при явном смещении. Разные моменты и значения повторов не приравниваются. [Регрессии слияния](../scripts/note-merge.test.mjs#L96), [три клиента на тестовом релее](../scripts/note-live-smoke.mjs#L306).

### Повторный прогон составных отказов

- **R1 — проверено на закреплённом Python-релее.** После первой страницы скана две онлайн-реплики обновили и удалили разные записи, а `floor` сдвинулся с `159` на `161`. Третья реплика отклонила продолжение старого скана, догнала новую границу и отправила одну независимую офлайн-правку. Все три совпали на `162`; перезапуск *внутри* скана остаётся отдельным сценарием. [Сценарий](../scripts/note-live-smoke.mjs).
- **D1 — проверено с управляемым отказом `StorageFull`.** Ошибка инъецируется перед записью второго слота; первый реально записан. Старый маркер не меняется, повтор успешен. На первом коммите оставшийся слот без маркера не принимается за пустое или подтверждённое состояние. Физический диск намеренно не заполняется. [Тесты Rust](../src-tauri/src/durable_file.rs).
- **D4 — воспроизведено и исправлено.** Три подряд отказа `stat` одного файла и чтения соседней папки не дают ложных событий удаления или повторного появления. Независимое изменение проходит сразу; настоящее удаление подтверждается только спустя два прохода. [Браузерный тест с IPC-подменой](../e2e/slag/vault_recovery.spec.ts).
- **Составная порча во время переноса.** При одновременной порче настроек, реестра и `state.json` целый журнал сохраняет запрет на показ незавершённого переноса. Промежуточный Markdown не меняется; без блокирующего окна можно записать другую заметку, прочитать её после перезапуска, сетевых попыток нет. [Протокол](../.agents/tasks/sync-compound-faults.md).

## Как превратить матрицу в покрытие

1. Сделать четыре подтверждённые пробы регрессиями: потеря подзадачи и неверный файл — первыми; ложные пункты папки/профиля и контракт напоминаний — следом. Для R1–R3 использовать реальные транзакции временного Python-релея; для D1/D3/D4 — управляемые ошибки I/O, а не случайные задержки. Для D2 сверять и ревизию, и физический каталог.
2. Прогонять детерминированные последовательности `правка / офлайн / потеря ответа / reconnect / TTL / перезапуск / сбой записи` с фиксируемым seed и журналом порядка событий. Сначала все попарные комбинации, затем целевые тройки: каскад × потеря квитанции × истечение ленты; медиа × смена области × перезапуск; повтор × разные пояса × офлайн. Любой провал — уменьшенный воспроизводимый сценарий, а не ещё один бесконтрольный случайный прогон.
3. Оракул: у каждого намерения проверяемый итог — принято один раз, уже выполнено, осталось в очереди или сохранено как альтернатива. Сверяем данные, физические проекции, ревизии, очереди и UX **после** восстановления. Для починившегося сбоя не нужен ручной выбор; при необратимом сбое нет молчаливой потери или подмены. Не измеряем готовность по одному сокету и не считаем все возможные сбои покрытыми.
