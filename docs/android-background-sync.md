# Фоновая синхронизация Android: диагностика

## Статус

На HONOR ALI-NX1 (Android API 35, WebView 157.0.8103.50) выполнены контроль, Home, выключенный экран, force stop и один принудительный глубокий Doze. Измерен разрыв между обычным фоном и системным idle; сценарий восстановления связи без открытия приложения остался непроверенным после сбоя USB/CDP. База для сравнения исходников — `71244956`; [доступный кандидат staging APK](https://github.com/wssdozh/slag-v2/actions/runs/45156798213) собран из `add9e2228`. Кандидат не равен базе: его результаты нельзя приписывать незамеренному `main`.

APK скачан и проверен локально: `com.slag.notes.staging.r45156798213`, Android Debug (подпись верифицирована), `allowBackup=false`, схема `slag-staging`, target SDK 37. SHA-256: `d05177d981d166501ce99b1b1ba2674b05d2a4b1d920890adda3882cfb850f87`. Workflow кандидата задаёт `127.0.0.1:18320` в конфиге и CSP; фактический адрес и чистую сессию нужно подтвердить после первого запуска.

В [движке](../src/lib/sync/syncEngine.ts) `bgSyncIntervalMinutes` задаёт резервный JS-тик, а не Android job. Значение `0` даёт 15 секунд; `10` и `30` — минуты. Здоровый WebSocket доставляет изменения без ожидания этого тика. В [манифесте приложения](../src-tauri/gen/android/app/src/main/AndroidManifest.xml) нет службы синхронизации; [onResume](../src-tauri/gen/android/app/src/main/java/com/slag/notes/MainActivity.kt) не инициирует догон. Это проверка кода, не результат прогона.

## Стенд и границы

Пользоваться [изолированным стендом реестра](note-registry-staging.md#изолированная-проверка-android): отдельный подписанный debug APK c уникальным `applicationId`, без backup, сеть только к локальному тестовому релею через USB `adb reverse`, отдельная временная SQLite, тестовый аккаунт и пустая комната. Второй клиент должен быть таким же изолированным. Сначала проверить пакет, версию, пустую сессию и адрес релея. Не использовать `com.slag.notes`, рабочую сид-фразу или релей. До изменения настроек Android (Doze, питание, сеть) согласовать тестовое устройство и способ восстановления; эти настройки могут влиять на весь телефон. Удалять только созданный проброс, не очищать системные логи и не трогать чужие профили.

Проверка подготовки без телефона: `node scripts/note-live-smoke.mjs <worktree релея feat/note-registry>` прошла на `06e6be7` с временной SQLite и тестовыми клиентами. Скрипт подтвердил догон после обрыва и HTTP-повтор без дубля; это не измерение Android, WebView или записи Android на диск. `npm run check` и веб-сборка `npm run build` прошли.

Отдельно проверен адрес, зашитый в APK: релей `06e6be7` запущен на `127.0.0.1:18320` с новой SQLite, `SLAG_REQUIRE_ACCOUNT_AUTH=true` и отключённым ботом; `/health` ответил `status=ok`, `authRequired=true`, `activeRooms=0`. После проверки процесс остановлен. Для прогона на телефоне создавать новую тестовую БД, а при моделировании обрыва повторно запускать релей с той же БД прогона.

На Windows ADB лежит в проектном SDK:

```powershell
$adb = Join-Path $env:USERPROFILE '.dsh-tools\android-sdk\platform-tools\adb.exe'
& $adb devices -l
```

Во всех дальнейших командах указывать выбранное устройство (`-s`) и отдельный staging-пакет. До начала записи зафиксировать Android API, версию WebView, commit APK, состояние батареи/зарядки, способ подключения и версию тестового релея. USB-зарядка может мешать естественному переходу в Doze: подтверждать состояние системным отчётом, а не только по выключенному экрану.

Контрольный Windows-клиент скачан из [изолированного прогона 44705308895](https://github.com/wssdozh/slag-v2/actions/runs/44705308895), ревизия `a6681fbd`. SHA-256: `302cb18405fe5008a804ea568db39c157f5d819ee9fc0f8b07800a1efb091781`. Он служит вторым участником обмена, но не эталоном для сравнения производительности Android. Перед входом всё равно проверить отдельный профиль и loopback-адрес. Клиент не запускался.

## Матрица

Сначала проверить синхронизацию в обе стороны при открытом приложении. Дальше на каждом шаге отправлять с другого клиента **новое** синтетическое изменение и проверять его ID. В каждом сценарии — три повтора, в воспроизводимом узком месте — десять на той же сети и нагрузке. Не трогать UI телефона, пока не проверили фоновую запись и курсор через `run-as` в debug APK. После этого отдельно измерить обновление ленты при возврате.

| Сценарий | Действия | Что отличает результат |
|---|---|---|
| Контроль | Оба клиента открыты, обмен в обе стороны. | Эталон задержки по каждому этапу и отсутствие дублей. |
| Home | Свернуть телефонное приложение без блокировки. | Телефон применил до открытия или догнал только после. |
| Экран выключен | Заблокировать экран; не считать это автоматически Doze. | Есть ли файл и записанный курсор до разблокировки. |
| Doze / экономия | Подтвердить состояние через `dumpsys deviceidle`; экономию измерять отдельно. | Различить остановку JS, сети и записи; восстановить изменённые настройки. |
| Обрыв / восстановление | Остановить и вернуть только тестовый релей с той же БД; повторить при свёрнутом приложении. | Снятие `adb reverse` само по себе не гарантирует разрыв уже открытого WS. |
| Force stop | Остановить только тестовый пакет, отправить изменение, проверить диск, затем открыть приложение. | Отдельный контроль холодного запуска; не смешивать с обычным сворачиванием. |
| Исходящий офлайн | Нативно сохранить одну правку без релея, свернуть, вернуть релей. | Намерение остаётся в журнале до доставки; после восстановления — одна принятая ревизия, без дубля. |

Время — от клика отправки по монотонным часам хоста до ближайшего опроса, а не точные моменты приёма. Данные сняты на Android `add9e2228` и Windows [45044112289](https://github.com/wssdozh/slag-v2/actions/runs/45044112289), ревизия `50e235b5`. Windows-артефакт `44705308895` не использован для обмена: в его отдельном профиле уже были данные. У обоих выбранных клиентов адрес проверен в UI и по локальным запросам, аккаунт и хранилище созданы специально для теста. Рабочий пакет не менялся. Doze снят в `finally`: подтверждено `mForceIdle=false`, `mState=ACTIVE`.

**Вывод:** на этом телефоне проблема не воспроизводится при обычном Home или погашенном экране без системного idle. В глубоком Doze изменение подтверждено релеем, но не применено до пробуждения, хотя процесс жив. Это указывает на участок между релеем и записью телефона; без отдельной метки приёма нельзя различить остановку сети, WebView или очередь применения. Не заменять живую доставку опросом 10/30/60 с: в обычном фоне запись уже доходит быстрее. Следующий узкий эксперимент — обрыв релея с офлайн-правкой и замер догона при восстановлении без открытия; для него нужен устойчивый ADB/CDP.

Коррелировать этапы по ID и ревизии; задержки считать по одной шкале времени либо отдельно на стороне процесса и хоста. В логах оставлять только тестовые ID и агрегаты, не сохранять тело, авторизацию или ключи. Отдельно отмечать пропуски, отсутствие метки и локально ожидающие намерения. Открытый WS, успех отправителя и видимая карточка не заменяют проверку диска получателя. Для оценки энергозатрат на коротком прогоне сравнивать число запросов/пробуждений при одинаковом окне, а не проценты батареи.

## Решение после замера

- Данные записаны в фоне, но лента отстаёт → исправить обновление UI, без сетевого опроса.
- Доставка застревает до возврата → проверить один догон в существующем движке, объединив lifecycle-сигналы и сохранив границы хранилища и поколения. Не поднимать второй писатель, не запускать полный `init()` на каждый фокус.
- Нужна доставка при приостановленном приложении → отдельно согласовать режим. [WorkManager](https://developer.android.com/develop/background-work/background-tasks/persistent/getting-started/define-work#schedule_periodic_work) даёт неточную периодику от 15 минут; у [видимой службы `dataSync`](https://developer.android.com/develop/background-work/services/fgs/timeout) есть лимит времени при работе приложения в фоне. 10/30/60 секунд — цель, не системная гарантия. Никаких разрешений и нового фонового клиента до измерений.
