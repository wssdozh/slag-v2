## 1. Концепция трех представлений папки

В SLAG v2 папка — это не просто директория на диске, а универсальный контекстный контейнер проекта, мысли или базы знаний. Внутри одной папки сосуществуют разные сущности:
* **Заметки (`note`)**: быстрые мысли, цитаты, сниппеты, войс-заметки, референсы.
* **Статьи (`article`)**: технические спецификации, аналитические записки, лонгриды с саммари.
* **Задачи (`task`)**: действия с дедлайнами, приоритетами, подзадачами и статусами.

Для эффективной работы с этим контентом пользователь может мгновенно переключать оптику восприятия в шапке папки (`FeedHeader`):

```text
┌────────────────────────────────────────────────────────────────────────┐
│  📁 Проекты / SLAG v2 (18)      [ 📜 Лента | 📋 Канбан | 📅 Календарь ]│
└────────────────────────────────────────────────────────────────────────┘
```

Каждое представление решает строго свою когнитивную задачу:
1. **Стрим (Лента)** — оперативный хронологический поток (режим «Поглощение и фиксация»).
2. **Канбан-доска** — процессный конвейер задач с индивидуальными стадиями для каждой папки (режим «Экзекушен и спринт»).
3. **Календарь** — временная проекция дедлайнов и планирование сроков (режим «Горизонт планирования»).

### Быстрые фильтры задач

В десктопной навигации «Сегодня», «Предстоящие», «Без даты» и «Выполненные» сужают текущую вкладку, не переключая её режим или папку. Повторный клик снимает фильтр. Область — папка с подпапками («Входящие» — только записи в самой папке, даже если до фильтра показано всё хранилище). Смена контентной вкладки, папки или хранилища сбрасывает фильтр; он не сохраняется на диск.

«Сегодня» включает открытые задачи на сегодня и просроченные, «Предстоящие» — открытые со сроком позже сегодня, «Без даты» — открытые без срока. Напоминание не заменяет срок. «Выполненные» проверяет статус, а не дату завершения. Календарь показывает просроченные и задачи без срока в существующей панели «Сроки», не назначая им новых дат. В ленте быстрый фильтр временно заменяет фильтр типа и «Скрыть выполненные», не меняя сохранённых настроек.

## 2. Архитектурное разграничение: Центр vs Правый Копилот

В интерфейсе проведено строгое функциональное разделение зон:

```text
┌─────────────────┬───────────────────────────────────────────┬───────────────────┐
│ Левый сайдбар   │ Центральная рабочая область               │ Правый сайдбар    │
│ (Дерево папок)  │ [ 📜 Лента | 📋 Канбан | 📅 Календарь ]    │ [Инфо | Ассистент]│
│                 │                                           │ (хоткей ⌘J)       │
│ - Навигация     │ - Контент текущей папки                   │ - Медиа-галерея   │
│ - Теги базы     │ - Фокусная работа с записями              │ - ИИ-Копилот      │
│ - Системные     │ - Перетаскивание карточек                 │ - RAG по папке    │
└─────────────────┴───────────────────────────────────────────┴───────────────────┘
```

* **Центральная зона** отдана на 100% под визуализацию данных папки (Стрим / Канбан / Календарь).
* **ИИ-Ассистент перемещен в правый сайдбар** (`FolderInfoPanel`):
  * **ТРИЗ-оператор «Разделение в пространстве»**: пользователь может двигать карточки на канбане или сверять дедлайны в календаре и одновременно вести диалог с ИИ в правой панели, задавая вопросы: *«Какие задачи в этой папке блокируют релиз?»* или *«Сформируй чек-лист по спецификации»*.
  * ИИ выступает как параллельный **Копилот**, не вытесняя рабочее полотно.

## 3. Канбан-доска по ТРИЗ: Решение проблемы смешанных сущностей

### 3.1. Физическое противоречие
При проектировании канбана для папки с разнородным контентом возникает конфликт:
* Заметки и статьи **должны быть на экране**, чтобы разработчик/автор видел контекст задач, ТЗ и источники.
* Заметки и статьи **не должны находиться в колонках выполнения**, чтобы не засорять процесс `Todo ➔ In Progress ➔ Done` карточками, у которых в принципе не может быть статуса «выполнено».

### 3.2. Операторы разрешения ТРИЗ
1. **Разделение в пространстве (Принцип №3: Местное качество)**:
   * **Зона процесса (75–80% ширины)**: классические процессные столбцы задач.
   * **Зона ресурсов / Док материалов (20–25% ширины, крайняя левая колонка)**: специальная колонка `[ 📚 Материалы папки ]`. В ней компактным списком отображаются карточки `note` и `article`.
2. **Фазовый переход (Принцип №35: Изменение параметров)**:
   * Перетаскивание карточки из колонки «Материалы» в любой процессный столбец автоматически трансформирует её:
     * Заметка меняет тип на `task`, получая соответствующий статус и чекбокс.
     * Либо создается связанная задача, сохраняющая ссылку на исходную статью в `linkedItemIds`.
3. **Динамичность и саморегуляция (Принцип №15 и №25)**:
   * Если в папке лежат только задачи (нет ни одной заметки или статьи), колонка «Материалы» **автоматически сворачивается**, освобождая экран под чистый канбан.
   * В шапке канбана предусмотрен тумблер `[ 📚 Материалы (N) ]` для ручного скрытия/раскрытия дока.

## 4. Индивидуальные столбцы для каждой папки

Каждая папка в SLAG v2 может иметь свой собственный жизненный цикл задач. Система не навязывает жесткую схему из трех колонок.

### 4.1. Примеры рабочих процессов
* **Программирование / Разработка**:  
  `[Бэклог] ➔ [В работе] ➔ [Код-ревью] ➔ [Тестирование] ➔ [Релиз]`
* **Контент / Статьи**:  
  `[Идеи] ➔ [Сбор фактуры] ➔ [Черновик] ➔ [Вычитка] ➔ [Опубликовано]`
* **Покупки и быт**:  
  `[Нужно купить] ➔ [Заказано] ➔ [В пути] ➔ [Получено]`
* **Универсальный процесс (по умолчанию)**:  
  `[К выполнению] ➔ [В процессе] ➔ [Сделано]`

### 4.2. Модель данных и обратная совместимость (Status Mapping)

Чтобы кастомные столбцы канбана не ломали базовые чекбоксы задач в стрим-ленте и мобильном интерфейсе, каждый пользовательский столбец мапится на один из трех базовых семантических статусов (`todo`, `in_progress`, `done`).

#### Спецификация `KanbanColumn` в `FolderMeta`:
```typescript
export interface KanbanColumn {
  id: string;              // Уникальный ID столбца (например, "review")
  title: string;           // Название столбца (например, "Код-ревью")
  statusMapping?: 'todo' | 'in_progress' | 'done'; // Семантический маппинг
}

export interface FolderMeta {
  path: string;
  name: string;
  description: string;
  icon?: string;
  isSystem?: boolean;
  
  // Настройки канбана для конкретной папки
  kanbanColumns?: KanbanColumn[]; 
  showReferenceColumn?: boolean;  // Состояние видимости дока материалов
}
```

#### Спецификация в `SlagItem` и Frontmatter `.md`:
```yaml
---
id: task_deploy_server
type: task
title: "Настроить Relay-сервер"
status: in_progress
kanbanColumn: review
dueDate: 2026-10-25
priority: high
tags:
  - devops
  - sync
---
```

* **Правило синхронизации**:
  * Если пользователь перетаскивает карточку в столбец `kanbanColumn: "review"` (у которого `statusMapping: "in_progress"`), то поле `item.kanbanColumn` выставляется в `"review"`, а поле `item.status` автоматически устанавливается в `"in_progress"`.
  * В стрим-ленте круглая кнопка статуса будет отображаться как «В процессе».
  * Если пользователь кликает по чекбоксу в стрим-ленте и переводит задачу в статус `done`, карточка на канбан-доске автоматически перемещается в первый доступный столбец с маппингом `done` (например, «Релиз» или «Готово»).

### 4.3. UI/UX управления столбцами канбана
* **Добавление столбца**: кнопка `+ Столбец` в правом краю доски. Открывает инлайн-ввод названия и селектор маппинга (`К выполнению / В работе / Сделано`).
* **Переименование**: клик по заголовку столбца переводит текст в инлайн-редактирование.
* **Сортировка стадий**: зажатие и перетаскивание заголовка столбца меняет порядок колонок слева направо.
* **Удаление столбца**: через контекстное меню `...` на заголовке. Если в столбце были карточки, система предлагает перенести их в соседний столбец или оставить без привязки к кастомному статусу.

## 5. Представление «Календарь»

Режим «Календарь» переводит фокус внимания на временную шкалу и дедлайны:

```text
┌────────────────────────────────────────────────────────────────────────┐
│  [ Сегодня ]   <  Октябрь 2026  >          [ Месяц | Неделя ]  [⚙ Фильтр]
├────────────┬────────────┬────────────┬────────────┬────────────┬───────┤
│ ПН 19      │ ВТ 20      │ СР 21      │ ЧТ 22      │ ПТ 23      │ СБ 24 │
│            │            │ ▢ Релиз v2 │ ▢ Бэкап DB │ ▢ Тесты    │       │
│            │            │   (high)   │            │            │       │
└────────────┴────────────┴────────────┴────────────┴────────────┴───────┘
```

### 5.1. Ключевые возможности календаря
1. **Привязка к датам**: карточки задач распределяются по ячейкам дней на основе поля `dueDate` (YYYY-MM-DD).
2. **Индикация приоритетов**: цветные плашки приоритета Linear-стиля (rose для `high`, amber для `medium`, zinc для `low`).
3. **Просроченные задачи (Overdue)**: дни до сегодняшней даты подсвечивают невыполненные задачи деликатной индикацией задержки.
4. **Drag & Drop планирование**:
   * Перетаскивание карточки задачи из одного дня в другой мгновенно перезаписывает `dueDate` в `.md` файле.
5. **Панель «Без дедлайна» (Unscheduled Drawer)**:
   * Выдвижная боковая шторка со списком всех задач папки, у которых не заполнено поле `dueDate`.
   * Пользователь может взять задачу из шторки и перетащить её на любой день календаря для мгновенного назначения дедлайна.
6. **Отображение заметок и статей**:
   * По умолчанию календарь фокусируется на задачах.
   * Тумблер `[ Включать заметки ]` позволяет отобразить на сетке дни создания заметок и статей (`createdAt`), давая визуальный тепловой журнал активности (activity log) по проекту.

## 6. Синхронизация представлений в Local-First архитектуре

Все настройки представлений и метаданные папок строго следуют принципу **Local-First**:
* Настройки столбцов канбана сохраняются в файле `folder.meta.json` внутри соответствующей директории хранилища (или в локальной реляционной таблице IndexedDB/Tauri).
* Положение карточки в канбане (`kanbanColumn`) и дедлайн календаря (`dueDate`) хранятся прямо в текстовом YAML Frontmatter каждого `.md` файла.
* Благодаря этому при открытии хранилища в Obsidian или переносе файлов через любой файловый менеджер данные остаются чистыми, читаемыми и не привязаны к проприетарной облачной базе.
