## 1. Архитектура сквозного шифрования (Zero-Knowledge E2E)

Синхронизация между устройствами пользователя (ноутбук, рабочий ПК, мобильный телефон) строится на принципе **нулевого доверия (Zero-Knowledge)**:

```
[Устройство А: Ноутбук]                          [Устройство Б: Смартфон]
   │                                                    ▲
   │ 1. Изменение заметки                               │ 5. Расшифровка
   ▼                                                    │    (AES-256-GCM)
[Локальное шифрование]                                  │
  Ключ из мастер-пароля                                 │
  (Argon2id + AES-256-GCM)                              │
   │                                                    │
   │ 2. Эфемерная зашифрованная дельта                  │ 4. Получение дельты
   ▼                                                    │
   ───────────────► [ Non-Storage Relay ] ──────────────┘
                     - Синхронизатор, НЕ хранилище
                     - Временный FIFO-буфер (TTL)
                     - Нулевое знание (Zero-Knowledge)
                     - Не хранит постоянную базу данных
```

### 1.1. Модель «Сервер-синхронизатор, а не хранилище» (Non-Storage Ephemeral Relay)
Фундаментальный постулат архитектуры SLAG v2 — **сервер никогда не является постоянным хранилищем пользовательских данных**:
* **Локальный суверенитет**: постоянным (персистентным) хранилищем данных являются исключительно устройства пользователя. Все заметки, статьи, задачи, медиавложения и метаданные папок физически живут в виде чистых текстовых `.md` файлов и `folder.meta.json` на диске клиента.
* **Роль Relay-сервера**: сервер выполняет функцию легковесного брокера дельт (Zero-Knowledge Transient Message Broker / Mailbox). Он служит связующим мостом для доставки изменений между устройствами.
* **Эфемерный буфер дельт и TTL**:
  * Когда Устройство А отправляет зашифрованное изменение файла, сервер помещает его во временную очередь доставки (Mailbox) для остальных спаренных устройств пользователя.
  * Как только все авторизованные устройства подтверждают получение дельты (`ACK`), зашифрованный пакет **немедленно удаляется** из памяти/буфера сервера.
  * Для устройств, находящихся временно в оффлайне, действует скользящее окно хранения (TTL, например, 7–14 дней). По истечении TTL невостребованные пакеты очищаются.
  * В случае долгого отсутствия устройства в сети (превышение TTL) синхронизация запускается через прямое сопряжение (Local Wi-Fi / P2P Sync или экспорт архива).
* **Синхронизация представлений и метаданных (Канбан, Календарь)**:
  * Все настройки представлений — пользовательские столбцы канбана (`kanbanColumns`), порядок колонок, скрытие дока материалов — сохраняются локально в `folder.meta.json`.
  * Положение карточек в столбцах (`kanbanColumn`) и дедлайны (`dueDate`) хранятся в стандартном Frontmatter `.md` файлов.
  * Сервер не требует схемы реляционных таблиц под канбан или календарь — он единообразно пересылает зашифрованные дельты метаданных и файлов.
* **Минимальные серверные требования**:
  * Сервер-синхронизатор может быть запущен на минимальном VPS или домашнем сервере (Docker-контейнер <64 МБ RAM, отсутствие тяжелых БД вроде PostgreSQL).

### 1.2. Генерация ключей и криптография
1. Пользователь вводит **Мастер-пароль** при первой настройке синхронизации.
2. Из мастер-пароля с использованием случайной соли (Salt) через `Argon2id` (или PBKDF2) генерируется 256-битный симметричный ключ шифрования.
3. Каждый файл (`.md` или медиавложение) шифруется по стандарту `AES-256-GCM` с уникальным вектором инициализации (IV).
4. На Relay-сервер отправляется полезная нагрузка:
   ```json
   {
     "vaultId": "vlt_user_123",
     "fileRelativePath": "Проекты/SLAG v2/Архитектура.md",
     "updatedAt": 1716034100000,
     "nonce": "base64_iv...",
     "encryptedData": "base64_ciphertext...",
     "authTag": "base64_tag..."
   }
   ```

## 2. Разрешение конфликтов (LWW & CRDT)

- **Стратегия Last-Write-Wins (LWW)**: на уровне отдельных файлов побеждает версия с наибольшим временем обновления `updatedAt`.
- **Защита от потери данных**: если обнаружено одновременное изменение файла на двух устройствах в оффлайне, создается дубликат с суффиксом `(Конфликт sync YYYY-MM-DD).md`, позволяя пользователю вручную объединить правки.

## 3. Мобильная адаптация на Tauri v2 (iOS / Android)

Приложение спроектировано для компиляции через **Tauri v2 Mobile**:

### 3.1. Адаптивная трансформация интерфейса
- **Десктоп (≥ 1024px)**: 3-колоночный сплит (Сайдбар + Стрим + Инфо-панель) с возможностью ресайзинга границ.
- **Планшет (768px – 1023px)**: 2-колоночный режим (Сайдбар + Стрим), правая панель открывается как всплывающая шторка справа.
- **Смартфон (< 768px)**:
  - Нижняя навигационная панель (Bottom Tab Bar): `Входящие`, `Папки`, `Поиск`, `Настройки`.
  - Полноэкранный просмотр ленты.
  - Нативный свайп вправо от левого края для возврата к списку папок.
  - Фокус-редактор с адаптацией под экранную клавиатуру.
