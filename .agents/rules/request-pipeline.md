# Четырехэтапный Пайплайн Запросов и Автономная Доставка

> Регламент сквозного прохождения любой задачи: от анализа входящего запроса до визуального тестирования.

---

## 1. Регламент 4-этапного пайплайна

Каждый запрос проходит 4 обязательных этапа строго последовательно:

```
[Этап 1: Изучение] ──► [Этап 2: Планировка] ──► [Этап 3: Реализация] ──► [Этап 4: Тестирование]
  - grep / glob          - Readiness Gate ≥90%   - Лестница Ponytail      - oxlint (0 warnings)
  - Сбор фактов          - ask_user_question     - Root-Cause Fix         - tsc -b && vite build
  - Карта зависимостей   - Чек-лист шагов        - Без костылей           - Playwright E2E
                                                                          - read_image скриншоты
```

---

## 2. Этап 1: Изучение задачи (Task Reconnaissance)

Запрещено писать код до исследования кодовой базы.

1. **Автономный сбор фактов**:
   - Найти затронутые файлы через `glob` и `grep`.
   - Проверить типы данных в `src/types/index.ts`.
   - Проверить состояние `src/context/AppContext.tsx` и `src/lib/storage.ts`.
   - Найти уже существующие функции, хуки и компоненты для повторного использования. Повторное написание утилит, уже имеющихся в проекте, запрещено.
2. **Запрет допроса пользователя по очевидным вещам**:
   - Не спрашивать пользователя о фактах, которые уже есть в репозитории (`package.json`, существующие компоненты, стили). Читать код самостоятельно.
3. **Определение зоны влияния**:
   - Точно зафиксировать: какие компоненты читают изменяемый стейт, какие файлы на диске затрагиваются.

---

## 3. Этап 2: Планировка (Specification & Readiness Gate)

Перед началом изменений агент формирует карточку готовности фичи (Feature Readiness):

```text
Feature Readiness:
- Цель: <что конкретно получает пользователь или система>
- Границы: <что меняется, а что гарантированно остается нетронутым>
- Контракты данных: <изменения в типах, frontmatter, хранилище>
- Критерии приемки: <проверяемые сценарии работы>
- Уверенность: <0-100%>
```

### Правило порога готовности (Gate $\ge 90\%$):
1. **Кодить при уверенности ниже 90% запрещено**.
2. Если логика интерфейса, сочетания клавиш или поведение данных не очевидны — задать вопрос через `ask_user_question`.
3. **Протокол вопросов**:
   - Один вопрос за шаг. Запрещено вываливать список из пяти вопросов подряд.
   - Давать 2–4 конкретных варианта с инженерными плюсами и минусами.
   - Рекомендуемый вариант ставить первым с пометкой `(Рекомендуется)`.
   - Никаких длинных вступлений: 1 строка описания дилеммы, затем конкретные опции.

---

## 4. Этап 3: Реализация (The Ponytail Ladder & Root-Cause)

1. **Лестница простоты Ponytail**:
   - `1. Нужно ли это вообще?` (YAGNI — убирать избыточные требования).
   - `2. Есть ли уже в проекте?` (Использовать утилиты из `src/lib/`).
   - `3. Решает ли стандартная библиотека / TS?` (Нативные методы строк, массивов, Web API).
   - `4. Решает ли установленный пакет?` (Использовать `lucide-react`, `@orama/orama`, не ставить лишние зависимости).
   - `5. Можно ли решить в одну строку?` (Писать одну строку).
   - `6. И только потом:` минимальный достаточный код.
2. **Поиск первопричины (Root-Cause Fix, без костылей)**:
   - Запрещено лепить слепые `?.` по десяти местам вызова, если проблема в источнике данных.
   - Запрещены пустые `try/catch`, глушащие ошибки.
   - Запрещены костыли с таймерами (`setTimeout(..., 100)`), маскирующие рассинхрон стейта. Использовать детерминированные эффекты и колбэки.
3. **Автономность выполнения**:
   - После прохождения Gate $\ge 90\%$ агент доводит задачу до конца без пауз на «мне продолжать?».

---

## 5. Этап 4: Тестирование (E2E & Скриншот-Аудит)

Окончание задачи требует обязательного прохождения 4 ступеней проверки:

1. **Статический линтинг**:
   ```bash
   npm run lint
   ```
   Требование: **0 warnings, 0 errors**. Предупреждения линтера приравниваются к ошибкам компиляции.
2. **Компиляция типов**:
   ```bash
   npm run build
   ```
   Требование: чистая сборка Vite и `tsc -b`.
3. **Автоматические Playwright тесты**:
   ```bash
   npx playwright test
   ```
   Требование: 100% тестов зеленые.
4. **Скриншот-аудит верстки на дефекты и сползание**:
   - При изменениях UI сделать скриншот через Playwright (`await page.screenshot(...)`).
   - Просмотреть полученное изображение через инструмент `read_image`.
   - Проверить по чек-листу: отсутствие горизонтального скролла, наложения блоков, обрезания текста, смещения кнопок и соблюдение контракта Linear (отсутствие рамок фокуса и чипсов на чипсе).
   - Подробный регламент: [[playwright-visual-testing.md]].

---

## 6. Передача контекста (Cross-Agent Handoff)

При передаче результатов работы оформлять блок:

```markdown
### Итог задачи (Handoff)
- **Симптом / Запрос**: <что требовалось сделать>
- **Первопричина / Архитектурное решение**: <почему сделано именно так>
- **Измененные файлы**: <список затронутых файлов>
- **Верификация**: <результаты lint, build, playwright и скриншот-аудита>
- **Остаток / Риски**: <что вынесено за рамки текущей задачи>
```

---

## 7. Критерии готовности (Definition of Done)

Задача считается выполненной только когда:
1. Поведение приложения строго соответствует согласованному плану.
2. `npm run lint` выдает 0 warnings и 0 errors.
3. `npm run build` компилируется без ошибок.
4. `npx playwright test` завершается со 100% успехом.
5. Скриншот проверен через `read_image` на отсутствие визуальных артефактов и сползания верстки.
6. Изменения зафиксированы атомарным коммитом по стандарту Conventional Commits на английском языке.
