# Разрешение Противоречий в Архитектуре и UI/UX (ТРИЗ)

> Методология ТРИЗ (Теория решения изобретательских задач) для автономных агентов и подагентов.  
> Запрет компромиссов, уродующих продукт. Устранение противоречий через ИКР и операторы разделения.

---

## 1. Базовый Принцип: Отказ от Ложных Компромиссов

В инженерии и дизайне агент часто сталкивается с кажущимся тупиком:
- *«Показать всё — будет визуальная свалка. Скрыть — пользователь потеряет данные».*
- *«Сделать канбан по папке — но там лежат статьи. Скрыть статьи — потеряем контекст проекта; запихнуть статьи в канбан — сломаем статусы Todo/Done».*

**Обычный разработчик ищет компромисс** (делает половинчатое решение, которое одинаково неудобно).  
**ТРИЗ-агент устраняет противоречие**: система получает достоинства обоих вариантов без их недостатков.

---

## 2. Формулировка Противоречий и ИКР

Перед тем как писать код или предлагать UX-паттерн, агент формулирует задачу в трех шагах:

```text
┌────────────────────────────────────────────────────────┐
│ 1. Техническое противоречие (ТП)                       │
│ «Улучшая параметр А, мы недопустимо ухудшаем параметр B»│
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ 2. Физическое противоречие (ФП)                        │
│ «Элемент X должен обладать свойством Y и anti-Y»       │
└───────────────────────────┬────────────────────────────┘
                            │
                            ▼
┌────────────────────────────────────────────────────────┐
│ 3. Идеальный Конечный Результат (ИКР)                  │
│ «Система САМА выполняет функцию без лишних сущностей»  │
└────────────────────────────────────────────────────────┘
```

1. **Техническое противоречие (ТП):**  
   Какая характеристика улучшается, и какая ухудшается?  
   *(Пример: улучшаем наглядность процессов через Канбан ➔ ухудшаем целостность базы знаний, так как статьи не имеют статуса выполнения).*
2. **Физическое противоречие (ФП):**  
   К какому физическому элементу системы предъявляются противоположные требования?  
   *(Пример: статьи и заметки ДОЛЖНЫ быть на экране канбана, чтобы давать контекст, и НЕ ДОЛЖНЫ быть в колонках канбана, чтобы не ломать логику статусов).*
3. **Идеальный Конечный Результат (ИКР):**  
   Идеальная система — это когда системы нет, а её функция выполняется.  
   *(Формула: Элемент сам решает задачу, используя уже имеющиеся ресурсы системы).*

## 3. Четыре Фундаментальных Оператора Разрешения ФП

Физические противоречия в коде и интерфейсах разрешаются исключительно четырьмя способами:

### 1. Разделение в пространстве (Separation in Space)
*Свойство Y действует в зоне A, а свойство anti-Y — в зоне B.*
* **UI-паттерн:** Разделение экрана на функциональные зоны с разным «местным качеством» (Принцип 3):
  * Зона процесса (Канбан задач: `Todo` / `In Progress` / `Done`).
  * Зона ресурсов (Док-панель / левая колонка материалов: статьи, войсы, референсы папки).
* **Архитектурный паттерн:** CQRS, вынос тяжелых бинарных вложений в отдельную директорию `.attachments/`, разделение чтения (Orama index) и записи (диск/IndexedDB).

### 2. Разделение во времени (Separation in Time)
*В момент времени T1 действует свойство Y, а в момент T2 — свойство anti-Y.*
* **UI-паттерн:** Переключатели режимов представления (View Modes):
  * Режим фокуса на действиях (`Канбан`) ⟷ Режим чтения/мышления (`Стрим` / `Статьи`).
  * Быстрый тумблер в шапке: `[Все материалы]` ⟷ `[Только активные задачи]`.
* **Архитектурный паттерн:** Debounce/throttle, отложенная индексация BM25 в Web Worker после завершения пользовательского ввода, ленивая подгрузка медиа.

### 3. Разделение по условию / Фазовый переход (Separation by Condition)
*В состоянии C1 элемент ведет себя как Y, а при наступлении условия C2 — как anti-Y.*
* **UI-паттерн (Динамический Drag & Drop / Конвертация):**
  * Карточка лежит в ресурсах как статическая заметка (`note`).
  * При перетаскивании в колонку `Todo` она испытывает фазовый переход: преобразуется в задачу (`task`) либо порождает задачу со ссылкой на исходную заметку.
  * Ввод строки `- [ ]` в композере на лету меняет тип записи с `note` на `task`.
* **Архитектурный паттерн:** Полиморфизм моделей через дискриминированные объединения (`type: 'note' | 'article' | 'task'`), адаптивные адаптеры хранилища (`indexeddb` vs `tauri`).

### 4. Разделение по структуре / Системный переход (Transition to Sub/Supersystem)
*На уровне системы действует Y, а на уровне элементов или надсистемы — anti-Y.*
* **UI-паттерн (Принцип «Матрешки», №7):**
  * Канбан отображает только задачи верхнего уровня, но карточка задачи выступает контейнером для связанных заметок и статей (`linkedItemIds`).
  * Статья отображается как документ, но внутри нее чекбоксы задач синхронизируются с общим трекером.
* **Архитектурный паттерн:** Вложенность контекстов, композиция хуков, LIFO-стек модальных окон и шторок.

## 4. Каталог Ключевых Приемов ТРИЗ для SLAG v2

| Прием ТРИЗ | Формулировка для UI/Архитектуры | Реализация в SLAG v2 |
|---|---|---|
| **№1. Дробление (Segmentation)** | Разделение монолитного экрана или сложного состояния на независимые части. | Изоляция ленты, композера, сайдбара и правой панели. Разделение папок и глобального Inbox. |
| **№2. Вынесение (Taking out)** | Выделение мешающей или редко используемой части во внешний слой. | Единое контекстное меню карточки вместо визуального шума из кнопок на каждой карточке. Вынос корзины в скрытую папку `.trash/`. |
| **№3. Местное качество (Local quality)** | Разные зоны экрана или типы данных имеют специализированное поведение. | Входящие имеют кнопки триажа (`AI Triage`), а проектные папки — метаданные описания для контекста агента. |
| **№7. Матрешка (Nested doll)** | Размещение одной сущности внутри другой без пложения новых таблиц. | Вложения (`attachments`) и подзадачи (`subtasks`) инлайнятся в YAML Frontmatter markdown-файла. |
| **№15. Динамичность (Dynamicity)** | Интерфейс сам адаптируется под наполнение. | Если в папке нет заметок (только таски), колонка «Материалы» канбана схлопывается автоматически. |
| **№22. Обратить вред в пользу** | Использование «мешающего» фактора как ресурса системы. | Не-задачные статьи на канбане не удаляются, а превращаются в базу знаний и контекстное сырье для задач. |
| **№25. Самообслуживание** | Система выполняет операции за счет собственных ресурсов. | Использование существующих тегов пользователя для ограничения фантазии LLM (`TAXONOMY FIRST`), хранение состояния в валидных `.md`. |

## 5. Протокол Действий Агента при Дилеммах (Contradiction Gate)

Когда пользователь или агент формулирует запрос вида *«Хочу фичу X, но мешает ограничение Y»*:
1. **Запрещено**: сразу писать промежуточный «костыльный компромисс».
2. **Шаг 1**: Сформулировать физическое противоречие: *«Компонент должен быть [X], чтобы [...], и должен быть [не-X], чтобы [...]»*.
3. **Шаг 2**: Применить 4 оператора разделения (в пространстве, во времени, по условию, по структуре).
4. **Шаг 3**: Проверить решение через лестницу простоты Ponytail (не созданы ли избыточные абстракции).
5. **Шаг 4**: При необходимости согласования с пользователем использовать регламент `ask_user_question` с четкими ТРИЗ-вариантами разрешения противоречия.
