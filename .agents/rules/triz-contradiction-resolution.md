# Разрешение Противоречий в Архитектуре и UI/UX (ТРИЗ)

Запрет гнилых компромиссов, уродующих продукт. Устранение противоречий через 4 оператора разделения.

---

## 1. Базовый принцип
Вместо половинчатого решения, одинаково неудобного в обоих сценариях, устранять физическое противоречие: элемент должен обладать свойством X для одной цели и не-X для другой.

---

## 2. Четыре оператора разделения

1. **Разделение в пространстве**: Свойство X действует в зоне A, не-X — в зоне B.
   - *UI*: Зона канбана (задачи: `Todo` / `Done`) отделена от зоны ресурсов (статьи, заметки, референсы папки).
   - *Архитектура*: Тяжелые медиафайлы вынесены в `.attachments/`; чтение (индекс Orama BM25) отделено от записи на диск.
2. **Разделение во времени**: В момент T1 действует свойство X, в момент T2 — не-X.
   - *UI*: Переключатель представлений `[Лента]` ⟷ `[Канбан]`.
   - *Архитектура*: Debounce пользовательского ввода; отложенная индексация в Web Worker после окончания набора.
3. **Разделение по условию (фазовый переход)**: В состоянии C1 поведение X, в C2 — не-X.
   - *UI*: Ввод `- [ ]` в композере на лету переключает тип записи с `note` на `task`. Перетаскивание заметки в канбан преобразует ее в задачу со ссылкой.
   - *Архитектура*: Полиморфные модели через дискриминированные объединения (`type: 'note' | 'article' | 'task'`).
4. **Разделение по структуре (подсистема / надсистема)**:
   - *UI*: Карточка задачи отображает связанные заметки через `linkedItemIds`, не перегружая канбан. LIFO-стек оверлеев.
   - *Архитектура*: Композиция хуков, инлайнинг подзадач в YAML Frontmatter markdown-файла.

---

## 3. Протокол действий при дилеммах
1. Сформулировать противоречие: элемент должен быть [X], чтобы [...], и [не-X], чтобы [...].
2. Выбрать один из 4 операторов разделения.
3. Проверить решение через лестницу Ponytail (не создавать лишних сущностей).
4. При необходимости согласования вызвать `ask_user_question` с 2–4 структурированными вариантами.
