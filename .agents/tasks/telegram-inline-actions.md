# инлайн-кнопки действий в телеграме

- **цель**: предложенное ассистентом действие (создать задачу, перенести, сменить статус) выполняется
  одной кнопкой под ответом в телеграме, без «жми «Применить» на карточке» — карточки в телеграме нет
- **трогаем**: `relay/server.py`, `relay/test_notifications.py`, `src/lib/notify/assistant.ts`,
  `src/lib/sync/{transport,syncEngine,account}.ts`, `src/context/hooks/useNotifyArm.ts`,
  `src/hooks/ui/useAssistantActions.ts`, `src/App.tsx`, `src/lib/ai/prompt.ts`
- **не трогаем**: UI карточек в приложении (там подтверждение уже есть), схему бандлов, хранилище
- **готово когда**: `python -m pytest relay/` зелёный, `npm run check` 0 предупреждений, `npm run build` проходит,
  в телеграме под ответом появляется кнопка, тап применяет действие на устройстве и убирает кнопку
- **уже выяснили**:
  - вопрос из бота отвечает устройство; релей моделей не запускает и сам ничего не применяет
  - ответ приходит через `POST /api/assistant/answer`, релей правит один бабл (`placeholder_message_id`)
  - телеграм хранит `text_link` только для http(s): `slag://` и `mailto` выбрасываются молча
  - `getUpdates` подписан на `allowed_updates: ["message"]` — без `callback_query` кнопки не нажмутся
  - в логах релея ответы 22:57 и 22:59 пришли за 7–10 с, то есть «лаг» был не в доставке; нужны метки стадий
    на устройстве (`assistant.stage`), чтобы отличать «модель думает» от «релей не доставил»

## контракт v1

1. `POST /api/assistant/answer` — тело получает необязательное поле `action`:
   `{ "id": "act_x", "label": "Применить", "summary": "«Купить кота», 14 ноя, Личное", "payload": { … } }`.
   Содержимое `payload` релей не разбирает и не хранит расшифрованным смыслом — он лишь возвращает его
   на устройство.
2. Релей кладёт `action` в строку запроса (`action_json`, `action_label`) и, отправляя ответ, добавляет
   разметку `{"inline_keyboard": [[{"text": label, "callback_data": "act:<requestId>"}]]}`.
3. `callback_query` с `data = "act:<requestId>"`: релей отвечает `answerCallbackQuery`, находит строку,
   проверяет, что чат владеет её route, и отправляет живым сокетам хранилища
   `{"type": "assistant_action", "id": "<requestId>", "action": { … }}`.
4. Устройство применяет действие тем же путём, что и карточку в приложении, и отвечает
   `POST /api/assistant/applied` `{vaultId, requestId, ok, text}`. Релей правит сообщение: к ответу
   добавляется строка `✓ применено: <text>` (или `не вышло: <text>`), клавиатура снимается.
5. Повторный тап по снятой кнопке и тап по устаревшему запросу (старше TTL) кнопку не оживляют:
   `answerCallbackQuery` говорит, что применять нечего.
6. Устройство со своей стороны не блокируется на подтверждении: ответ модели уходит в телеграм сразу,
   вместе с предложенным действием.

## после работы (сторона устройства)

- **файлов больше, чем в «трогаем»**: появился `src/lib/notify/assistantAction.ts` (сборка `action` для
  `/answer` и строгий разбор эха), `src/lib/sync/accountTypes.ts` (типы `AssistantActionPayload`,
  `AssistantAppliedPayload`). `useNotifyArm.ts` не трогали: `/clear` и вопросы уже были подключены.
- **`payload` — это `SuggestedAction` целиком**, релей его не разбирает. Тип зафиксирован в
  `accountTypes.ts`, сборка в `toAssistantAction`. Перед отправкой `actionState` сбрасывается в
  `suggested`: `executeSuggestedAction` молча выходит на `applied`/`executing`, и кнопка «применила бы»
  ничего.
- **`id` кнопки не обязан быть случайным**: взяли `act_<requestId>`, чтобы повторная отправка ответа не
  родила вторую кнопку с другим id.
- **`label` упирается в лимит телеграма** (64 байта на текст кнопки) — режем до 40 символов. В контракте
  лимита нет, релей должен знать, что длинную подпись модели укоротили мы, а не он.
- **`POST /api/assistant/applied`: форма ответа не описана.** Типизировали как
  `AssistantAppliedResult { reason?: 'already' | 'gone' }` — релею достаточно вернуть `{}` или `204`.
- **разбор эха — не доверяем кадру**: `parseAssistantAction` проверяет тип действия, заголовок и типы
  скаляров, и только из них собирает объект. Поле `batchItems` (расписание по задачам) не перечитывается:
  исполнитель применяет переносы через `batchUpdateItems`.
- **отчёт о пакетном действии неполный**: `executeSuggestedAction` возвращает последнюю тронутую запись,
  поэтому при `batch_update` строка `✓ применено:` называет один пункт, а не весь пакет. Если нужен счёт —
  исполнителю придётся возвращать `{ item, appliedCount }`, это правка карточки, не этой задачи.
- **не решено на релее: тап применяют все живые сокеты хранилища.** Кадр `assistant_action` уходит в
  комнату целиком, как `assistant_clear`, поэтому два включённых устройства применят одно нажатие дважды.
  Для вопросов выбор один — `assistant_probe`; здесь его нет. Варианты: слать только устройству, которое
  ответило на вопрос (запомнить его по `requestId`), либо гасить дубль по `applied` (первый победил) и
  считать это нормой. Пока что на устройстве стоит дедуп по `requestId` в пределах одной сессии.
- **логи стадий** на устройстве: `Telegram question received` → `Telegram answer model started` →
  `Telegram answer model done` (с `durationMs`) → `Telegram answer sent` → `Telegram action applied`
  / `not applied`; scope `NOTIFY`, у каждой строки `requestId`.
- **не проверено живьём**: реальный тап в телеграме, снятие клавиатуры, TTL, два устройства в комнате.
