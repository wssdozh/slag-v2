# SLAG: самовосстановление после прерванной записи

- **цель**: после сбоя Windows SLAG сам открывает то же хранилище с привычным редактированием; исправные Markdown не зависят от прочтения общего файла состояния. Синхронизация возвращается без перепривязки, когда можно подтвердить непрерывность журнала.
- **трогаем**: на фазе 1 только эту карточку. Зоны для оценки: чтение Markdown/YAML и производных индексов; нативное сохранение файлов; версия состояния, очередь и восстановление проекций реестра.
- **не трогаем**: рабочее хранилище, установленное приложение, релей и его данные. Не переносим заметки в БД, не предлагаем копию хранилища, не заменяем целиком его содержимое архивом, не сбрасываем неизвестную очередь. Пользовательский интерфейс истории и восстановление после отказа всего диска не входят в первоначальное предложение.
- **готово когда**: в изолированном хранилище после точечного сбоя на границах записи и повторного запуска: 0 ручных действий для открытия; все исправные заметки открыты; создание/редактирование в том же хранилище переживает следующий запуск; ни одна подтверждённая пользователю как сохранённая правка не теряется от прерванной записи на исправном носителе; восстановление идемпотентно; удалённое не воскресает и очередь не теряется, не дублируется и не объявляется пустой без проверки. Отдельно проверить падение процесса и жёсткую перезагрузку на Windows (не считать первое заменой второму). Поведение при старой порче без подходящего журнала — на обсуждении.
- **уже выяснили**: на момент инцидента оставались 106 читаемых Markdown, корневой `state.json` состоял из нулей. Тайминг согласуется с гипотезой о прерванной записи ОС, но не доказывает точный механизм. `syncCurrentVaultFs()` строго читает `pendingFolderProjection` до сканирования; этот барьер относится к незавершённым папочным операциям, его нельзя считать пустым на ошибке. Текущая запись JSON — временный файл рядом и rename, без явного flush. Строгая запись заметок пользуется тем же примитивом, нестрогая пишет напрямую. Журнал реестра уже фиксирует намерения до проекции и умеет отдельные повторные применения. Старый снимок не подтверждает отсутствие более новых локальных операций. Совместимость с внешними редакторами не позволяет считать нормальный Markdown повреждённым лишь по несовпадению со старым хэшем. ZIP-бэкап — отдельная функция, не протокол завершения транзакции.

## Фаза 1 — гипотеза и референсы

Если SLAG отделит чтение и локальную работу с заметками от исправности служебного состояния и защитит сохранения от прерванной записи, после сбоя пользователь продолжит работу в том же хранилище без ручных действий. Метрики в тестах со сбоями: число действий после запуска, число доступных исправных заметок и потери правок, отмеченных сохранёнными; для синка отдельно — пропуски/дубли и возможность автостарта при доказуемой непрерывности.

- [Obsidian: хранение](https://obsidian.md/help/data-storage) — Markdown первичен для локальной работы, кэш метаданных пересобирается; не копируем ручную команду пересборки для аварийного старта.
- [Obsidian: File recovery](https://obsidian.md/help/plugins/file-recovery) — локальные снимки изменённых заметок с ограниченным хранением; не копируем ручной выбор версии для однозначной аварии, не считаем периодический снимок гарантией последнего сохранения.
- [SQLite: атомарная фиксация](https://www.sqlite.org/atomiccommit.html) — должный порядок flush и автоматически восстанавливаемая незавершённая транзакция; берём принцип, не переносим Markdown в БД и не пишем новый журнал рядом с существующим без необходимости.
- [Syncthing: File Versioning](https://docs.syncthing.net/users/versioning.html) — хранит прежние версии при входящих изменениях; такой подход сам по себе не защищает локальную запись SLAG.

Предложение: сначала разделить производные данные и незаменимое состояние, не подменять пропавшие операции набором заметок. Для перезаписи — запись новой версии с принудительным сбросом на диск, безопасная замена и проверяемая предыдущая версия. Автоматом восстанавливать только то, для чего есть однозначное основание (целостность, нужная версия/поколение, необходимая цепочка изменений); не подменять исправные заметки старыми снимками при внешних правках или осознанном удалении. Для прерванной транзакции использовать существующий журнал, где это применимо. Это варианты для обсуждения, не подтверждённый план.

Вердикт: делать узкое самовосстановление при сбое записи, а не новый механизм восстановления всего хранилища. Сейчас ручной путь в приложении отсутствует; целевой — 0 действий после обычного запуска. Открытые границы: локальные правки при невалидной цепочке синка; гарантии для несохранённого текста; нужна ли совместимость с уже повреждённым состоянием без новых резервов.

## Фазы 2–3 — согласованный путь

Обычный запуск → та же лента → обычное создание/редактирование. Ноль дополнительных шагов. Сохранение подтверждается только после фиксации на диске. При недоказанном состоянии очереди продолжает работать локальный vault, а синк отключён до доказуемого восстановления; используем существующий статус. Если диск недоступен для записи, не выдаём «сохранено». Никакого нового интерфейса версии, копии vault или кнопок восстановления.

- A: нативная фиксация файлов, проверяемое поколение служебных данных, тесты прерывания. Только Rust и платформенный адаптер.
- B: локальный компонент восстановления, чтение Markdown, защита и подтверждение локальных сохранений. Только storage и вызывающие хуки.
- C: отдельная привязка, миграция журналов, запрет синка при неизвестной истории, MCP и headless. Только sync/MCP/Node.
- Интеграция: сохранение той же области до/после перезапуска, матрица целостности, изолированный сценарий 106 Markdown, карта и документация. Без Goal, релиза и правок пользовательских данных.

## Реализация и проверка

- Синтетическое воспроизведение: до правки оболочка показывала «Хранилище пустое» при 106 исправных Markdown. После правки обычная лента открывается без меню восстановления, новая заметка и правка переживают два запуска. Ошибка записи оставляет ввод в композере. Отдельно проверена миграция исправного конфига и очереди, а также повторная порча настроек при целых защищённых поколениях.
- `npm run check`, `npm run build`, 317 скриптовых тестов, два теста Rust на Windows и целевые проверки Playwright прошли. Шесть падений широкого Playwright-прогона воспроизведены на исходной ветке: медиа, календарный drag-and-drop, фильтры входящих, превью статьи, фильтр ассистента и обзор календаря.
- Не проверены: жёсткое отключение Windows VM и остановка staging-приложения посреди фактической записи, Android на устройстве, нативный p95. Сокращён повторный обход дерева и объединены параллельные чтения секций; числовой выигрыш не заявляем. Полное восстановление уже потерянной очереди без надёжного источника невозможно, поэтому синхронизация в этом случае остаётся остановлена. Выпуск не выполнялся.
