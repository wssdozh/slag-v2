# Проверять синхронизацию после порчи диска и долгого офлайна

- **цель**: находить потерю правок, небезопасное возобновление доставки и блокировку локальной работы до релиза.
- **трогаем**: нативные тесты поколений, Playwright fixture/сценарии восстановления, loopback smoke реестра, CI, карту синхронизации.
- **не трогаем**: рабочую комнату, реальные профили устройств, данные пользователя. Скрипты не принимают путь к хранилищу; в relay smoke передаётся только checkout исходников тестового сервера.
- **готово когда**: seeded-порчу можно повторить, побайтовое восстановление или безопасный отказ доказаны, UI открывает и сохраняет локальные записи в защитной паузе, три реплики на тестовом релее сверяют реальные проекции после возврата офлайн-устройства.
- **уже выяснили**: файлы поколений защищают очередь и привязку отдельно от `state.json`; восстановление не должно считать потерянную очередь пустой. Режим комнаты определяет, какие записи идут через реестр; отсутствие доказанной базы не является конфликтом полей.

## Прогон

- `node scripts/note-live-smoke.mjs <checkout slag-relay на 06e6be7> --offline` — три реплики, реальное шифрование, WebSocket/HTTP, штатная очистка временной SQLite. Лента ещё доступна: `8 → 118`, ручной разбор не нужен. Лента истекла: `floor=147`, после доставки независимых правок и повторного запуска все на `150`. Локально сохранены два недоказуемых варианта, которые не мешают другим правкам. Оба режима smoke прошли также с `SLAG_SMOKE_RTT_MS=40`. Профиль тестируется в комнате с `sharedRecords`; это не настройка рабочей комнаты.
- `cargo test --manifest-path src-tauri/Cargo.toml --lib durable_file::tests` — 8 тестов на Windows, из них seeded-матрица покрывает 72 случая. Один seed: задать переменную `SLAG_DISK_FAULT_SEED` десятичным числом и отфильтровать `seeded_sync_file_faults`. Тест сам создаёт чистый корень в системной временной папке; путь к vault передать нельзя.
- `npx playwright test e2e/slag/vault_recovery.spec.ts` с `PLAYWRIGHT_WORKERS=1` — 6 сценариев, в том числе защита введённого текста при отказе записи и локальная работа после недоступности трёх поколений. IPC подменён, интерфейс и логика клиента настоящие; байты нативных файлов проверяются отдельным Rust-набором. Нет проверки физического отключения питания или нагрузки на реальные профили Windows/Linux/Android.
- `npm run check`, `npm run build` и `npm run test:scripts` прошли; после сборки в скриптовом наборе 333/333 без пропусков. В [CI](../../.github/workflows/ci.yml) прописаны Rust-тесты на Linux, оба Python-relay smoke на закреплённом исходнике сервера и Playwright в штатном наборе `e2e/slag`. Фактические прогоны выше локальные; новую сборку на устройства не устанавливали.

Получилось не так, как ожидалось: при сканировании эталонов клиент терял даже доказанный прямой переход и ошибочно ставил правку на проверку. Регрессия воспроизвела это до исправления. Теперь прямой переход подтверждается по аутентифицированному `baseRevision`; цепочка из нескольких отсутствующих переходов и `delete`/`restore` не выводятся из совпадений текста. Параллельные разные изменения одного дерева или одной общей записи всё ещё используют строгую проверку ревизии, а не слияние полей.
