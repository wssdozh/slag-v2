# Разбор конфликтов реестра и индикация доставки

- **цель**: разбирать только содержательные конфликты; по журналу понимать причину, а по карточке — состояние отправки.
- **трогаем после согласования**: сравнение значений реестра и представления с диска, местные логи операции, полноэкранное сравнение и индикатор карточки.
- **не трогаем**: рабочую комнату и данные пользователя; защиту от перезаписи новой ревизии, семантику удаления/восстановления и атомарность папочных операций. Без отдельного движка слияния.
- **готово когда**: эквивалентные после известной нормализации заметки дают ноль ручных конфликтов при совпадении базы; различия текста и значимых свойств видны в сравнении; устаревшую правку нельзя применить после смены ревизии; одинаковые отображаемые версии с одной подтверждённой ревизией имеют одинаковый статус при отсутствии местной очереди и конфликта; по логу видно источник, стадию и результат без содержимого заметки.
- **уже выяснили**: `fields: ["update"]` — вид операции, а не имя поля. `sameNote` сравнивает разобранные объекты, не YAML; наличие ключа со значением `undefined` может менять результат, хотя при записи JSON ключ исчезает. Текущий конфликт-UI — JSON в настройках; существующий полноэкранный diff рассчитан на AI-патч и покрывает пять свойств. ## Обсуждение (без правок приложения)

Гипотеза: если сравнивать один смысловой формат на всех устройствах и показывать реальный diff вместо JSON, пользователю не придётся вручную разбирать смену формата; мерим ноль ложных конфликтов в проверочных сценариях и открытие сравнения за один клик от строки конфликта.

Путь: «Конфликты» → «Сравнить» → полноэкранное сравнение «На релее / Моя правка» → осознанное действие или закрытие без изменений. При совпадении текста показывать сразу свойства; на телефоне один дифф вместо двух узких колонок. Сравнение переиспользует существующий визуальный слой. Применение требует проверки показанной ревизии; пакет папок решается целиком.

Референсы: [отдельный diff из списка конфликтов VS Code](https://code.visualstudio.com/docs/configure/settings-sync#_resolve-conflicts), [стрелки синхронизации отдельно от успешного статуса в Dropbox](https://help.dropbox.com/sync/sync-icons-windows).

Диагностика: после устойчивой записи логировать конфликт/эквивалентность/решение; по тому же `intentId`/`opId` связывать источник, базу, квитанцию, отказ и повтор; группам — агрегат. Для контурной точки использовать диагностику сравнения по запросу, не журнал на каждый рендер.

Вердикт: делать урезанно — общая консервативная нормализация, отдельный экран на существующем диффе, понятные состояния.

## Согласованные границы реализации

Клиент: два решения без ручного слияния полей; проверить показанные ревизии для обоих действий; отдельно отметить фактическую сетевую отправку и логировать жизненный цикл без пользовательских данных.

Админка: статус комнаты и переход `legacy → frozen → registry`, отмена до активации. Снимки и сверка локально; в UI импортируется только зашифрованный seed. Проверка поколения и состава писателей, SQLite-бэкап до активации, атомарная запись на живом релее, повтор с перечитыванием статуса. Общий лимит загрузки не повышать. Не делать мастера сбора снимков или обновления уже активного реестра. Рабочую комнату и dev-релиз не трогать.

## По итогам реализации

- Эквивалентность касается известных YAML-умолчаний и отсутствующих необязательных значений. Совпадение тела не разрешает повтор от устаревшей ревизии, в том числе после удаления и восстановления.
- Админский переход остаётся операторской процедурой: манифест писателей изготовляется локальным bootstrap, HTTP переносит только запечатанный пакет. Первый полный прогон релея выявил лимит размера модулей; логику перенесли в существующие модули, лимит не меняли.
