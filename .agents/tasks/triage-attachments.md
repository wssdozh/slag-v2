# одноимённые вложения в тексте

- **цель**: два разных image.webp показывают свои изображения в карточке и редакторе.
- **трогаем**: общий resolver attachmentEmbed, MarkdownRenderer, fullscreen/attachmentEmbeds, точечный фильтр галереи ItemCard по resolved ids (scope согласован с lead), целевой e2e.
- **не трогаем**: модель SlagAttachment, миграции, vault, useFullscreenDraft, Composer, поиск, тему и конфиги.
- **готово когда**: npm run check; целевой e2e на 5322 одним worker; screenshot просмотрен.
- **уже выяснили**: item_1794894118153 имеет две ссылки ![[image.webp]] и два разных файла с одинаковым name. resolver всегда возвращает первый; карточка на скрине дублирует первую картинку вместо второго скрина.

---

ожидаемое: legacy-ссылки распределяются по одноимённым вложениям в порядке списка; однозначные id/relativePath разрешаются непосредственно. одиночные уникальные ссылки можно повторять. build запрещён прямым заданием.

факт: терялись не записи SlagAttachment, а их идентичность при name-only resolution. скрин карточки дублирует первую картинку, второй реальный скрин совсем другой. галерея тоже скрывала лишнее по имени — теперь только по resolved id. порядок считается по полному документу, не зависит от курсора/viewport. сохранение и модель не менялись.

проверки: npm run check — 0 warnings/errors; целевой e2e на 5322/1 worker — passed, сверяет bytes в feed/editor, roundtrip markdown/frontmatter, id/path repeats, unique name repeats и missing. screenshots просмотрены read_image. первый запуск теста упал из-за ошибочного названия меню «Редактировать» вместо «Фокус-редактор», исправлено.

ограничение: намеренный повтор первого из нескольких одноимённых файлов невозможно восстановить из одинаковых legacy tokens; для явного выбора поддерживаются id/relativePath. реальные vault-файлы только читались; native desktop и весь e2e suite не проверялись.
