# Ленивая подгрузка байт вложений в видимой части ленты

- **цель**: байты вложения читаются только те, что нужны кадру; просмотрщик дорешивает кадр, которого ещё нет, и не показывает пустой `src`.
- **трогаем**: `src/components/Feed/FeedList.tsx` (дека из метаданных, без прелоада папки), `src/components/UI/ImageLightbox.tsx` (кадр ±1), `src/components/RightPanel/useFolderMedia.ts` + `FolderMediaTabs.tsx` (модель без резолва, плитка/строка решают сами), `src/hooks/media/useAttachmentSrcOnDemand.ts` (один общий узкий резолвер + один общий observer сетки с фолбэком), `e2e/support/mediaProbe.ts` и один спек `e2e/slag/media_request_budget.spec.ts`.
- **не трогаем**: `ItemCard` (свой резолв по карточке), `AttachmentStore`/`indexedDb` (эвикция, запись, кэш url — слайс storage).
- **готово когда**: `PLAYWRIGHT_WORKERS=1 SLAG_E2E_PORT=18846 npx playwright test e2e/slag/attachment_resolve_budget.spec.ts e2e/slag/lightbox_lazy_slides.spec.ts` зелёный в одном воркере, `tsc -p config/tsconfig.app.json` и oxlint по изменённым файлам чистые.
- **уже выяснили**:
  - лента резолвит всю папку: 96 уникальных вложений из IndexedDB при 15 смонтированных карточках, 51 вложение вне окна = 639 183 Б из 1 203 168 Б (замер `attachment_resolve_budget`, байты считаются как base64 × 3/4, не по JS heap);
  - повторные чтения (`cumulativeGets` = 474) реальны и приходят от нескольких независимых потребителей: прелоад папки, хук каждой карточки, `PinnedBanner`, двойной монтаж эффектов в dev-сборке. Точную долю StrictMode не приписываем;
  - в просмотрщике байты кадра теперь резолвит сам кадр, а монтируются только активный и его соседи: на открытии кадра 3 из 5 прочитаны ровно `lazy_1` и `lazy_3`, кадр 0 не читается даже после листания вправо;
  - готовый `url` из колоды по-прежнему главнее: фото, которое лента уже разрешила, просмотрщик повторно не читает.
  - **лента больше не прелоадит папку**: дека собирается из метаданных (`url` только у инлайн-байтов, `sourceItem` у всех), байты берут карточки окна и сам кадр просмотрщика. Замер `attachment_resolve_budget` до/после: `uniqueAttachmentIds` 96 → 45 (= 15 смонтированных карточек × 3), `offWindowIds` 51 → **0**, `offWindowPayloadBytes` 639 183 → **0**, `cumulativeGets` 474 → **90**; с закрытой панелью те же 45/0/90. Листание в просмотрщике при этом доходит до заметки вне окна и получает настоящие байты — это отдельный ассерт, а не следствие прелоада.
  - **важно на будущее**: временный ассерт `offWindowIds > 0` снят. Гейт теперь `offWindowIdsWithoutPanel === 0` в проходе с закрытой панелью `perf(right-panel)` (и `uniqueAttachmentIds <= windowChunk * PER_NOTE`); сквозное число с панелью осталось как измерение, но гейтом не является.
  - второй потребитель той же папки — правая панель «Инфо» (`FolderProfile` → `RightPanel/useFolderMedia.ts`). Она смонтирована и видна в дефолтной раскладке (`folderProfileShown: true`), рисует сетку медиа папки, поэтому её полный резолв был её законным объёмом, а не случайной утечкой. Замер до правки панели: с панелью 474 гета и 96 уникальных id, без панели 282 гета при тех же 96 id.
  - панель переведена на плиточный резолв (слайс `perf(right-panel)`): модель папки больше не читает байты, плитка просит свой файл при подходе к колонке (`usePanelAttachmentSrc`, `rootMargin: 120px`), строки аудио/файлов — только пока их вкладка открыта. Дефолтная раскладка: профиль 288×1561 в колонке 320×966, сетка 3 колонки, плитка 92×92; в кадре 24 плитки из 40, панель спросила 24 разных вложения из 42 (ровно видимые), `pane_audio`/`pane_file` при закрытых вкладках — ноль. На уровне IndexedDB это убрало вклад панели: `cumulativeGets` в базовой линии 474 → 282, то есть ровно столько же, сколько с закрытой панелью. Открытие вкладок «Аудио»/«Файлы» по-прежнему запрашивает их байты — это закреплено в тесте.
  - **операционное правило репо**: `git stash` в этом репозитории не использовать — стек стэшей общий для всех worktree, и перепутанный pop уже утащил чужие правки в чужое дерево. Базу сравниваем в отдельном worktree или диффом между коммитами/ветками, без stash/reset/checkout по рабочим файлам.
  - слайс сокращён: три спека и два хука свёрнуты в один спек `media_request_budget` (156 строк) + общий хелпер `mediaProbe` (98 строк) и один хук `useAttachmentSrcOnDemand` (резолвер + один observer сетки, с фолбэком «все плитки видны» без `IntersectionObserver`). `rootMargin: 120px` только предзагружает ближние к колонке плитки, состав списка не меняет. Итоговые числа того же прогона: `feedIds` 45, `feedOffWindow` **0**, `paneIds` 24 при `paneVisibleTiles` 24 из 96 плиток, аудио/файл — 0 до открытия вкладок, `readIds` 45 / `readBytes` 563 985.
  - observer сетки дошёл до финального вида: callback-ref возвращает cleanup и снимает плитку с наблюдения (React 19 вызывает его вместо `null`), увиденная плитка снимается сразу (`unobserve`), observer пересоздаётся при повторном attach после StrictMode, а `seen` привязан к ключу текущего списка — смена папки с тем же числом фотографий начинает с пустого множества. Резолвер хранит ответ по идентичности `id + path + mime`, а не по одному id.
  - регресс на замену добавлен в тот же спек: вторая папка «Проекты» с таким же числом фото (96), переключение через строку дерева папок — новые плитки обязаны получить байты (без сброса `seen` по ключу они бы не разрешились).
  - правка внутри той же папки: `seen` не сбрасывается, а пересекается с текущими id, поэтому удержанные плитки (их ref не перепривязывается и observer их уже отпустил) остаются «увиденными» и не гаснут; удалённые id вычищаются, фолбэк без `IntersectionObserver` считается при рендере (без `setState`), поздние записи observer отбрасываются по `entry.target.isConnected`. В спеке — шаг «добавили фото в текущую папку»: плитки остаются загруженными, новая дорешивается при прокрутке.
  - соседние спеки, не относящиеся к слайсу, на этой базе красные и требуют отдельной проверки на базовом worktree: `feed_thumbs` ждёт hero-картинку > 300 px, тогда как карточка рисует плитки 80 px (`ItemImages` без импортёров), а планшетный тест `media_viewer` ждёт кнопку «Открыть видео», которой в `src` нет.

---

что оказалось не так, как думали:

- клик по плитке невозможен без байт (`AttachmentTile` отключает кнопку), поэтому сценарий «байты пришли после первой отрисовки» строится на заметке, где часть вложений разрешена, а часть — нет; иначе просмотрщик просто не открыть.
- отдельные поля `relativePath`/`mimeType` в `LightboxImage` не нужны: из текущих продюсеров колоды либо есть `sourceItem` (`FeedList`, `ItemCard`), либо url всегда готов (правая панель, `AttachmentStrip`, который вдобавок размазывает само вложение). Резолвер поэтому смотрит только в `sourceItem.attachments` по `image.id`; поля из типа убраны, чтобы не заводить второй источник правды.
- готовый ответ резолвера нельзя хранить без привязки к файлу: тот же React-ключ получает новую `relativePath` (вложение пересохранено) или теряет готовый `url`, и байты прошлого файла показались бы вместо нового. Кэш ответа теперь `{ sourceKey (id+path+mime), url }` и отдаётся только при совпадении ключа; отказ промиса — `mediaLog.warn` и пустой кадр, без `setState`.
- цель CSS-зума — рамка кадра, а не картинка: она смонтирована и получает transform независимо от того, пришли ли байты (и решается по типу самого кадра, а не по активному `currentImage`).
- сборка `ViewerVideo` внутри общего кадра требует `src` до первого кадра: видео без байт показывает чёрный кадр, а не пустой `<video src="">`.
- ни одно действие просмотрщика не использует `image.url` иначе как через сам кадр и `key`: скачивания/меню по url в нём нет, `handleOpenFocus` открывает заметку.

что осталось:

- `AttachmentStore.urlCache` без вытеснения и без `revokeObjectURL` — отдельный слайс storage, здесь не трогали;
- финальный медиа-дифф целиком на ревью у лида до интеграции.
