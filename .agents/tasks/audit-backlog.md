# аудиты: что смотреть дальше, по убыванию риска

список не «когда-нибудь почистить», а «где следующий такой же баг». составлен после аварии
2026-11-18; размеры файлов — на `a0c6c09`.

## 1. `src/lib/sync/syncEngine.ts` — 1222 строки

семь обязанностей в одном классе: конфиг, транспорт (ws, ping, реконнект), presence, pull,
push, initial sync, вложения. авария жила ровно здесь: порядок `init()` против чтения диска.

что сделать: вынести транспорт (сокет, реконнект, backoff), сессию (init / switchVault /
`initGeneration`), presence и вложения в отдельные модули. публичный API движка не меняется.

## 2. `src/lib/sync/localBookkeeping.ts` — 540 строк

у каждого леджера **два** пути записи: секция `state.json` и `prefs`-фолбэк, выбор по `onDisk()`.
плюс миграция старых ключей. `syncedIds` жил здесь и пересевался на каждом старте — это и есть
цена такого устройства: второй источник правды незаметно становится главным.

что сделать: один store (`SyncSectionStore`), один путь записи, фолбэки убрать. миграцию оставить
одноразовой и явной.

## 3. `src/lib/sync/syncSection.ts` — 268 строк

`mergeSectionState` сливает две копии по записям: файл выигрывает, старый blob добивает дыры.
это второе мнение о чужих данных — ровно то, из-за чего леджеры расходятся молча.

что сделать: посмотреть, нужен ли merge вообще, или хватит «файл — истина, blob читается один раз
при миграции и удаляется». после удаления `syncedIds` вопрос стал заметно проще.

## 4. три очереди записи

`prefs.queueFlush`, `vaultFiles.queueStateWrite`, `settingsStore` coalescing queue. два
продакшн-бага подряд — `settings.json.tmp` и `state.json.tmp` — оба из «два писателя на один файл».
`writeJsonAtomic` теперь не может столкнуться именами, но потеря ключа при read-merge-write между
двумя окнами осталась.

что сделать: один файл — один владелец. у `settings.json` и `secrets.json` писателей два
(главное окно и быстрый композер), и это надо закрыть не лучшим rename, а одним писателем.

## 5. `src/lib/sync/applyBundle.ts` — 430 строк

одна цепочка `if/else if` по типам изменений, все правила LWW внутри. удаление/восстановление и
надгробия теперь покрыты тестами, остальное — нет: ошибку в порядке применения видно только в
браузере.

что сделать: разложить по типу изменения (по функции на `item`/`folder`/`workspace`/`memory`/
`draft`) и вынести чистые правила LWW в тестируемые функции.

## 6. `src/lib/storage/index.ts` — 916 строк

`importSyncedVaultData` смешивает запись на диск, сверку с локальными правками и папки.
17 веток `!isTauri()` / `usesStateFile()` в `src/lib/storage/*.ts` — две модели хранения в одном
классе.

что сделать: вынести импорт в отдельный модуль записи; ветки браузера свести к одному адаптеру.

## 7. `src/lib/sync/pushBundle.ts` — 361 строка

`pack()` дедуплицирует по хешу, а прямые `changes.push` (удаления, черновики, папки, вложения) —
нет. один bundle может нести один id дважды. сейчас это безвредно: приёмник разрешает по штампу.
но это правило, которое держится на удаче.

что сделать: один `pack` для всех изменений, включая удаления.

## 8. потерянный пуш

`pushLocalChanges` умеет выходить раньше времени (`initialSync` loading/error, receive-only,
не готов движок, **и теперь «vault не прочитан»**), и только ветка «идёт пуш» ставит `pushDirty`.
остальные выходы не планируют повтор. сейчас это прикрыто тем, что `init()` заканчивается пушем,
но это снова порядок вызовов, а не правило.

что сделать: один `schedulePushAfter(reason)` вместо флага, либо честный `return false` наружу.
