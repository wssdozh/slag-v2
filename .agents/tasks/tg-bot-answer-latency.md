# ответ бота в телеграме: p50 11 с → ≤5 с

- **цель**: вопрос из чата получает ответ за p50 ≤ 5 с, p90 ≤ 8 с (замер 14.11: p50 11.3 с, p90 49 с)
- **трогаем**: `relay/server.py`, `src/lib/sync/syncSocket.ts`/`useNotifyArm.ts` (поллинг), `src/lib/ai/orchestrator.ts`, `src/lib/ai/prompt.ts`, `src/lib/notify/assistant.ts`, `relay/tg.py` + тесты релея
- **не трогаем**: стриминг в пузырь (этап 2), транспорт апдейтов (webhook не быстрее), `risky`-инструменты, тексты стадий
- **готово когда**: `npm run check`, `npm run build`, `python -m pytest relay/` зелёные; тот же sql-замер даёт p50 ≤ 5 с и p90 ≤ 8 с
- **уже выяснили**: замерено на проде (см. §3). основное время — не телеграм и не модель: треть ожидания это проба/доставка, а хвост в 20–90 с это вопросы, которые попали в сокет, который не отвечает.

## 1. гипотеза

если перестать отдавать вопрос сокету без свежего признака жизни (и сократить поллинг `/api/assistant/pending` с 30 до 5 с), а в режиме `minimal` считать повестку и статистику фактами вместо вызова инструментов, то p50 падает с 11.3 до ≤5 с, а p90 с 49 до ≤8 с — при том же качестве ответа.

мерим: `latency_ms` события `assistant.answer` в `delivery_events` (`relay/server.py:3839`), окно 5–7 дней до и после, плюс `answered_at - created_at` в `assistant_requests`.

## 2. референсы

- **доставка апдейтов**: long polling и webhook одинаково быстрые (kerit.cloud, gramio) → транспорт не трогаем, webhook не берём (плюс https-эндпоинт и риск повторной доставки при медленном хендлере).
- **лимиты Bot API**: приватный чат ≈ 1 сообщение/с, `editMessageText` считается так же (tdlib#3034, activepieces) → стриминг в пузырь только с троттлингом ≥1.5 с.
- **стриминг**: не ускоряет генерацию, режет время до первого видимого текста в 10–30 раз; порог «потока мысли» ~1 с (Nielsen, clickhouse).
- берём: сначала убрать реальные секунды (P1–P3), стриминг — этапом 2 и только по остатку. не берём: webhook, фреймворк поверх Bot API, отдельный воркер.

## 3. замер прода (14.11, 32 ответа за двое суток)

| метрика | значение |
|---|---|
| p50 ожидания до ответа | **11.3 с** |
| average | 22.0 с |
| p90 | **49 с** |
| max | 127 с |
| ответов | 32 (17 minimal, 15 risky) |

разбор по сегментам:

| сегмент | факт |
|---|---|
| вызов модели | 1.4–6.2 с, медиана ~2.6 с |
| размер промпта | 5.4–10k токенов, обычно ~8.5k |
| вызовов модели на вопрос | 1–3 (не 1) |
| накладные (всё, что не модель) | ~3–3.4 с даже на лучшем примере: 6 с ожидания при 2.6 с модели |
| хвост 20–90 с | запросы, где модель не вызывалась вообще (ответ из локальных фактов) — вопрос ждал, пока его подберут поллингом |

что это значит:

1. `ask_22b260a9` (6 с) = 1 вызов модели 2.6 с → 3.4 с ушло на плейсхолдер, пробу и доставку ответа. потолок даже с «мгновенной» моделью — около 4 с.
2. `ask_51fb5529` (12 с) = 2 вызова, 9 с модели. второй вызов — инструмент, без которого в `minimal` можно обойтись.
3. хвост — не модель: там 0 вызовов, а ожидание 20–90 с. ровно то, что делает `_bot_question`, когда проба никого не нашла, и `PENDING_PULL_MS = 30_000` в `useNotifyArm.ts`.
4. в комнате 4 устройства (пк, ноут, телефон, pet-node), поэтому проба срабатывает почти всегда, а её таймаут — 1.5 с (`ASSISTANT_PROBE_TIMEOUT_SECONDS`).

## 4. ux-путь

сейчас: вопрос → «🔎 ищу устройство…» → «⌛ передал на «…»» → «✍️ печатает ответ…» → 11 с тишины (в хвосте — до минуты) → ответ.

после: вопрос → «✍️ печатает ответ…» → 3–5 с → ответ. стадию «передал на» показываем только когда устройств больше одного.

## 5. приоритеты

| # | что | impact | трудозатраты | риск |
|---|---|---|---|---|
| P1 | не отдавать вопрос мёртвому сокету + поллинг 30 → 5 с | огромный: p90 49 → ≤8 с | 2 файла | средний: дубль вызова модели на переизбрании |
| P2 | `minimal` без инструментов + промпт-вилка | высокий: −2–4 с на p50 | 3 файла | средний: ответ не должен обеднеть |

## 6. вердикт

**делаем P1–P3**. это реальные секунды и почти весь хвост. стриминг — после повторного замера: если p50 встанет на 3–4 с, он не нужен; если останется 6+, вернёмся к нему с цифрами.

## prd

**что меняется**
- **P1a**: сокет, от которого не было ни одного кадра (`ping`, `bundle`, `ack`) за последние N секунд, не считается кандидатом на вопрос. `conn.last_frame_at` ставится в общем обработчике входящих кадров.
- **P1b**: если выбранное устройство не прислало ни `assistant_stage: thinking`, ни ответ за ~4 с — релей один раз переизбирает устройство (без повторной пробы у того же) и переотправляет вопрос. поздно пришедший ответ первого устройства отбрасывается как «already» (это уже работает).
- **P1c**: `PENDING_PULL_MS` 30 000 → 5 000 в `useNotifyArm.ts`. это `GET /api/assistant/pending`, пустой ответ почти ничего не стоит.
- **P2**: в `runChat` при `channel === 'telegram'` инструменты не передаются вовсе; блок «статистика хранилища» и «повестка» собираются на устройстве и идут в промпт фактами; из системного промпта в этом режиме выпадают разделы про инструменты, которых нет (сохранение, декомпозиция, фильтр, гайд).
- **P3**: `TelegramBot` держит одно https-соединение на процесс (переоткрытие на обрыве); вопрос на устройство уходит параллельно с отправкой плейсхолдера, а не после.

**границы**
- `risky` и путь приложения в целом не меняются (кроме общего промпта — вилка только для `telegram`+`minimal`).
- формат ответа, карточки действий, `[[ссылки]]`, `/clear`, obey `retry_after` — без изменений.
- стриминга нет.

**edge cases**
- все сокеты stale → вопрос честно ждёт поллинг (5 с) и отвечается, а не висит 30.
- одно устройство в комнате → проба по-прежнему пропускается, но свежесть кадра проверяется.
- устройство ожило и ответило после переизбрания → ответ отбрасывается как «already», второй раз модель не зовём.
- `minimal` без инструментов, а вопроса про заметки → правило `notesRestricted` отвечает «в этом режиме видно только задачи» (уже есть).
- модель не вызвала инструмент, но фактов не хватило → текстовый ответ, как сейчас.

**acceptance criteria**
1. «что на сегодня» и «сколько заметок» в `minimal` → в логах устройства ровно одна строка `Agent round 1/3 … finished`, ответ содержит те же числа, что отдавали инструменты.
2. вопрос, который ушёл в мёртвый сокет, доезжает до живого устройства за ≤5 с (в `delivery_events` видно `assistant.question` dispatched и `assistant.answer` подряд).
3. `assistant.stage` на один вопрос ≤ 1 (сейчас 17 событий на 24 вопроса + повторы).
4. `npm run check`, `npm run build`, `python -m pytest relay/` зелёные.
5. повторный замер: p50 ≤ 5 с, p90 ≤ 8 с.

## декомпозиция

1. **P1a/P1b — релей**: `last_frame_at` на соединении, фильтр кандидатов, `_answer_watchdog` на 4 с с одним переизбранием; тесты в `relay/test_notifications.py` (мёртвый сокет не выбран; живой выбран; переизбрание не дублирует ответ).
2. **P1c — клиент**: `PENDING_PULL_MS` → 5000, комментарий почему.
3. **P2 — факты**: `buildSystemPrompt(..., facts?, toolSections: false)`, `runChat` без тулз для telegram, `assistant.ts` собирает строку фактов из `storage.getVaultStats()`.
4. **P3 — сеть**: keep-alive в `tg.py` с переоткрытием; порядок «вопрос, потом плейсхолдер» в `_bot_question`.
5. **замер**: тот же sql после релиза, цифры сюда.

## замер (тот же запрос до/после)

```sql
SELECT COUNT(*) n,
       MIN(latency_ms) min_ms,
       ROUND(AVG(latency_ms)) avg_ms,
       MAX(latency_ms) max_ms
FROM delivery_events
WHERE kind='assistant.answer' AND at > strftime('%s','now') - 7*86400;
```

p50/p90 — сортировкой: `SELECT latency_ms FROM delivery_events WHERE kind='assistant.answer' ORDER BY latency_ms;` и взять середину и 90-й процентиль руками (32 строки — глазами быстрее, чем изобретать sql).

## event map

- `assistant.answer.latency_ms` — главная метрика.
- `assistant.question` / `assistant.stage` — сколько кадров и правок на вопрос.
- лог устройства `Telegram answer model done` — цена модели отдельно от сети.
- `Agent round N/3` — что круг остался один.
