# убрать шум в логе синка: replay, битые вложения, чужие черновики

- **цель**: лог ноутбука после догона не тонет в WARN; битое вложение жалуется один раз за сессию;
  устройство, у которого остался удалённый черновик, узнаёт об удалении и не присылает его снова
- **трогаем**: `src/lib/sync/transport.ts` (код ошибки `bundle_replay`), `src/lib/storage/attachments.ts`
  (предупреждение о байтах, которых нет), `src/lib/sync/applyBundle.ts` + `src/lib/sync/syncEngine.ts`
  (повторное объявление удаления черновика)
- **не трогаем**: протокол релея и формат бандла — меняется только клиентская реакция; чужие
  устройства обновляем не мы, они исправляются, когда применяют присланный delete
- **готово когда**: `npm run check` (0 warnings), `npm run build`, и в логе с ноутбука после
  догона `bundle_replay` не WARN, а debug
- **уже выяснили** (лог `slag-2026-11-17.log`, ноут после 4 дней офлайна):
  - `bundle_replay` ×4 — это `WS_ACK_TIMEOUT_MS = 2500` в `src/config/sync.ts`: http-фолбэк
    переотправляет бандл раньше `server_ack`, релей ловит дубликат по `bundleId`. данные при
    этом доставлены, следом в логе всё равно `confirmed by relay`;
  - 334 `Ignored stale composer draft` за 4 минуты: 245 бандлов из истории релея за 16-е и 77
    живых. пир присылает `updatedAt <= deletedAt` — то есть держит копию, которую тут уже удалили;
  - 37 `Attachment bytes are not on this device`: два файла (`att_1793180839386thrj…json`,
    `att_1794748867552kqnl…webp`) отсутствуют на диске, запрос в комнату ушёл один раз, кулдаун
    24 ч (`ATTACHMENT_REQUEST_COOLDOWN_MS`). предупреждение повторяется на каждый рендер ленты.

---

после работы: что оказалось не так, как думали, и что осталось.

- **думали** «пиры держат копию и присылают её снова».  по факту основная масса — не пиры, а
  история релея: из 334 stale-строк 245 приходили бандлами от 16-го числа, то есть клиент после
  четырёх дней офлайна вычитал их из истории. живыми были 77 — и вот для них повторное
  объявление удаления как раз и нужно, оно отправляет пиру свежий `deletedAt`, после чего тот
  выкидывает черновик из своего outbox (компакция в `Outbox.enqueue` заменяет upsert на delete
  по тому же `kind:id`).
- **проверено на ноуте** после `npm run build && npm run build:desktop:fast` и перезапуска:
  `Re-announced deleted composer draft` — 1, `Ignored stale composer draft` — 1 (было 334),
  `bundle_replay` — 0 WARN, `Attachment bytes are not on this device` — 1 (было 37 на рендер,
  плюс повторный запрос байтов у релея по-прежнему уходит раз в сутки на файл).
- **осталось**:
  - fullscreen-черновики (`fullscreen:<itemId>`) тем же лечением не покрыты — там та же ветка
    `updatedAt <= deletedAt`, но живого трафика почти нет, поэтому решение то же, что и для
    composer, делать половинчато не стал;
  - http-фолбэк всё ещё переотправляет бандл через `WS_ACK_TIMEOUT_MS = 2500`: если когда-нибудь
    захочется меньше трафика на догоне, поднимать именно его, а не гасить лог;
  - два файла (`att_1793180839386thrj…json`, `att_1794748867552kqnl…webp`) на ноуте так и не
    появились: запрос уходит раз в сутки, ответа нет — это не лог, а мёртвые данные, лечится
    чисткой ссылки в заметке.
