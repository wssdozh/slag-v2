# бэклог синхронизации без огромных ответов

- **цель**: дочитывать очередь с вложениями на слабом канале, не скачивая её одновременно по двум транспортам.
- **трогаем**: HTTP-пагинацию релея, согласование транспорта, планирование выгрузки вложений и тесты.
- **не трогаем**: шифрование, правила слияния, старый протокол для клиентов без опции, данные хранилища.
- **готово когда**: бюджет режет страницы без потерь, тяжёлый одиночный бандл проходит, повтор идёт с того же курсора, старые клиенты по-прежнему работают.
- **уже выяснили**: HTTP без бюджета собирал до 100 бандлов в один ответ, параллельно websocket отправлял ту же очередь. Размер исходного ответа с ноута не замерен; эти механизмы подтверждены по коду и воспроизведены на тестовых данных.

---

Старым клиентам нельзя выдавать короткую страницу по весу: они считают её концом ленты. Новый контракт явно запрашивается. Выгрузку вложений нужно будить только после снятия `pendingPull`, иначе проверка снова её откладывает.

Нативный `0.2.5-dev.59` установлен на пк, ноутбуке и Android. На живом релее старая страница из 100 бандлов весила 66 284 257 байт; при новом бюджете первый ответ по тому же набору — 86 308 байт полезной нагрузки. Ноут принял полный повтор с пк (133 изменения); ошибок `HTTP bundles fetch failed` в логе проверки нет. Все 11 заметок, которые есть на пк и отсутствуют на ноуте, имеют на ноуте отметки удаления новее содержимого на пк. Это отдельный конфликт данных, а не недокачанная страница. На момент проверки листья: пк 100, ноут 89, Android 90. Отметки удаления и содержимое вручную не менялись.
